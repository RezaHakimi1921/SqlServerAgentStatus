# سند اینسایت و پیش‌بینی DBA

**موضوع:** نیازمندی سامانه بینش، پیش‌بینی و پیشنهادهای پیشگیرانه برای SQL Server DBA
**تهیه‌کننده:** Manus AI
**تاریخ:** ۱۶ نوامبر ۲۰۲۶
**ارتباط با اسناد دیگر:** مکمل «سند نیازمندی از سمت مانوس» و «سند قابلیت‌ها» است. تمرکز این سند، تبدیل داده‌های پایش به Insight قابل‌توضیح و اقدام کنترل‌شده است.

## ۱. هدف محصول

هدف، ساخت محیطی برای DBA است که تنها وضعیت فعلی را نمایش ندهد. سامانه باید روند تغییرات را نگه دارد، احتمال نزدیک‌شدن به مشکل را زودتر اعلام کند، شواهد و علت احتمالی را نشان دهد و گام بعدی مناسب را پیشنهاد کند.

سامانه در هر پیشنهاد باید به این پرسش‌ها پاسخ دهد: چه چیزی ممکن است دچار مشکل شود؟ چه زمانی یا با چه احتمالی؟ چه داده‌ای این پیش‌بینی را پشتیبانی می‌کند؟ پیامد آن برای workload چیست؟ چه اقدام کم‌ریسکی می‌توان انجام داد؟ چه چیزی را DBA باید پیش از اقدام بررسی کند؟ پس از اقدام، اثر آن چگونه سنجیده می‌شود؟

پیش‌بینی تضمین جلوگیری از خرابی نیست. تا وقتی داده کافی وجود ندارد، کیفیت داده باید آشکار باشد و به‌جای پیش‌بینی قطعی، سامانه «نشانه»، «ریسک» یا «پیشنهاد بررسی» نمایش دهد.

## ۲. اصول طراحی

### ۲.۱ شواهد قبل از توصیه

Insight باید به نمونه‌های داده، بازه زمانی، metricهای مؤثر و روش تشخیص قابل دسترسی متصل باشد. برای مثال، «فضای فایل با روند ۳۰ روز اخیر ممکن است طی ۱۲ روز به آستانه هشدار برسد» باید تاریخچه اندازه فایل، شیب رشد، فضای قابل‌استفاده و فرض ثابت‌بودن روند را نشان دهد.

### ۲.۲ تفکیک مشاهده، تشخیص، پیش‌بینی و اقدام

هر مورد باید نوع مشخص داشته باشد: مشاهده از داده خام؛ تشخیص الگوی غیرعادی؛ پیش‌بینی با افق و عدم قطعیت؛ یا پیشنهاد اقدام. سامانه نباید پیش‌بینی را به‌عنوان رخداد قطعی، یا پیشنهاد را به‌عنوان دستور اجراشده نشان دهد.

### ۲.۳ اقدام انسانی برای تغییرات حساس

نسخه اول Insight فقط‌خواندنی باشد. تولید اسکریپت و اجرای تغییر، قابلیت جداگانه و اختیاری است. هر اقدام تغییردهنده schema، ایندکس، فایل یا تنظیمات باید پیش‌نمایش، مجوز، تأیید صریح، پنجره نگه‌داری، audit log، روش بازگشت و بررسی پس از اجرا داشته باشد.

### ۲.۴ حداقل اثر بر SQL Server

جمع‌آوری داده باید زمان‌بندی‌شده، قابل تنظیم و کم‌هزینه باشد. کارهای پرهزینه مانند بررسی فیزیکی fragmentها یا جمع‌آوری planها نباید به‌صورت مکرر و بی‌محابا اجرا شوند. نرخ polling بر مبنای نوع داده و حساسیت workload تنظیم شود.

### ۲.۵ قابل‌فهم‌بودن اطمینان

هر Insight شامل سطح اطمینان و دلیل آن باشد؛ عواملی مانند طول تاریخچه، تعداد نمونه‌ها، وقفه در جمع‌آوری، restart اخیر، تغییر schedule یا کمبود پوشش داده باید اطمینان را کاهش دهند. از دقت کاذب و درصدهای بدون پشتوانه پرهیز شود.

## ۳. مدل داده و جریان هدف

جریان پیشنهادی:

`SQL Server و منابع عملیاتی` ← `Collector زمان‌بندی‌شده و read-only` ← `اعتبارسنجی و نرمال‌سازی` ← `Repository تاریخی و metadata` ← `محاسبه روند/baseline/risk` ← `Insight قابل‌توضیح` ← `داشبورد، هشدار و پیشنهاد اقدام` ← `تأیید DBA برای اقدام حساس`.

Collector از Query Store، catalog/system views، DMVهای مجاز، تاریخچه SQL Agent، اطلاعات فایل‌های دیتابیس و در صورت مجازبودن منابع سیستم‌عامل داده می‌گیرد. هر مشاهده باید به `instance`, `database`, `object`, `query`, `job` یا `file` مرتبط باشد و `observed_at`, `source`, `collection_status`, `duration` و version اطلاعات را ثبت کند.

Repository باید داده خام لازم برای بازتولید محاسبه، خلاصه‌های زمانی برای نمودارها، Insightها، وضعیت رسیدگی و audit اقدام‌ها را جداگانه نگه دارد. retention برای هر گروه داده تعریف شود؛ متن کامل query یا command ممکن است حساس باشد و باید با دسترسی محدود یا redaction نگه‌داری شود.

## ۴. حوزه‌های Insight

### ۴.۱ Queryها و workload

**داده‌های ورودی:** Query Store در صورت پشتیبانی و فعال‌بودن، query text با سیاست دسترسی مناسب، planها، تعداد اجرا، مدت/CPU/خواندن و نوشتن منطقی، memory و waitهای موجود؛ زمان جمع‌آوری، database و تغییرات plan نیز ثبت شود. Query Store می‌تواند تاریخچه query، plan و آمار runtime را برای بررسی الگو و regression نگه دارد؛ در نسخه‌های SQL Server، تنظیم پیش‌فرض Query Store متفاوت است و availability/وضعیت آن باید پیش از فعال‌سازی بررسی شود [1].

**Insightهای پیشنهادی:** افزایش پایدار مدت یا CPU نسبت به baseline؛ regression پس از تغییر plan؛ رشد logical reads؛ queryهای پرتکرار با هزینه تجمعی بالا؛ wait غالب و queryهای مشارکت‌کننده؛ تفاوت workload ساعت اوج با baseline همان بازه.

**پیشنهادهای احتمالی:** بررسی planهای اخیر و قبلی، بررسی تغییرات schema/statistics، بازبینی predicate یا join، ارزیابی indexهای موجود و missing-index candidate، و تست اصلاح در محیط غیرتولیدی. سامانه در نسخه اولیه نباید خودکار plan را force یا query را rewrite کند.

**نمایش:** اثر کل workload و اثر هر اجرا جدا باشند؛ رتبه‌بندی فقط بر اساس میانگین مدت انجام نشود. برای هر مورد تعداد اجرا، کل مصرف، median/percentile و بازه مشاهده نمایش داده شود.

### ۴.۲ SQL Server Agent Jobها

**داده‌های ورودی:** اجراها و Stepها، نتیجه، مدت، schedule، زمان شروع/پایان، retry، وابستگی‌های قابل‌شناسایی، owner و metadata اهمیت/تیم.

**Insightهای پیشنهادی:** احتمال دیرکرد نسبت به موعد؛ افزایش مدت در اجرای اخیر؛ شکست‌های تکرارشونده یا افزایش نرخ شکست؛ اجرا نشدن در schedule مورد انتظار؛ هم‌پوشانی Jobهای سنگین؛ زنجیره‌ای از Jobهای پایین‌دستی که به شکست بالادستی وابسته‌اند.

**پیشنهادهای احتمالی:** بررسی پیام و Step شکست‌خورده، زمان‌بندی مجدد، بررسی هم‌زمانی با maintenance، تعیین owner یا runbook، و بازبینی وابستگی‌ها. اجرای مجدد یا توقف Job در این نسخه صرفاً پیشنهاد باشد، نه اقدام خودکار.

**توضیح پیش‌بینی:** زمان معمول باید با Jobهای مشابه از نظر روز هفته و ساعت مقایسه شود. اگر تعداد نمونه کم باشد، فقط «مدت فعلی از میانگین اخیر بیشتر است» گزارش شود و برچسب پیش‌بینی قطعی داده نشود.

### ۴.۳ دیسک، فایل‌ها و ظرفیت

**داده‌های ورودی:** اندازه تخصیص‌یافته فایل data/log، فضای استفاده‌شده و آزاد داخل فایل، تنظیم growth و max size، رویدادهای رشد، فضای آزاد volume از منبع مناسب و در صورت امکان اطلاعات latency/I/O. فضای داخل فایل دیتابیس با فضای آزاد volume یکی نیست و باید در UI جداگانه نشان داده شود.

**Insightهای پیشنهادی:** تخمین زمان رسیدن به آستانه فضای آزاد؛ رشد log در کنار عدم امکان reuse؛ تکرار autogrowth یا growthهای بزرگ؛ حجم‌های پرشدونده؛ تفاوت میان رشد allocated size و used space؛ فشار احتمالی در TempDB.

**پیشنهادهای احتمالی:** بررسی workload/transaction و log backup، پیش‌تخصیص اندازه مناسب در پنجره نگه‌داری، بررسی max size و فضای volume، و ارزیابی محل فایل. برنامه نباید shrink را به‌عنوان راه‌حل پیش‌فرض پیشنهاد کند؛ رشد و shrink مکرر می‌تواند هزینه کارایی و fragmentation فایل‌سیستم ایجاد کند و Microsoft مانیتورینگ رشد و برنامه‌ریزی اندازه را توصیه می‌کند [2].

**روش پیش‌بینی:** روند کوتاه‌مدت و بلندمدت با نرخ رشد robust و بازه عدم‌قطعیت ارائه شود. تغییرات عمده یک‌باره، purge، restore، load و maintenance باید به‌عنوان نقاط تغییر علامت‌گذاری شوند. در صورت نوسان بالا یا تاریخچه کم، زمان پرشدن نمایش داده نشود و تنها روند/ریسک گزارش شود.

### ۴.۴ رشد جدول، پارتیشن و ایندکس

**داده‌های ورودی:** snapshot اندازه تخصیص‌یافته و استفاده‌شده به تفکیک object، index و partition؛ row count تقریبی، فضای row/LOB/row-overflow و زمان snapshot. DMVهای partition اطلاعات page و row-count تقریبی هر partition را فراهم می‌کنند؛ جمع دوره‌ای این داده‌ها برای تشخیص روند لازم است [3].

**Insightهای پیشنهادی:** رشد سریع یا تغییر نرخ رشد جدول؛ تمرکز رشد در یک partition؛ افزایش حجم index نسبت به base table؛ رشد فضای LOB؛ پیش‌بینی ظرفیت مورد نیاز در افق انتخابی.

**نمایش:** اندازه جاری، تغییر مطلق و درصدی، نرخ روزانه/هفتگی، تاریخچه snapshot، نسبت data به index و سطح دقت اندازه‌گیری. برای جدول‌های پرتغییر، ردیف‌شماری کامل اجرا نشود؛ شمارش approximate مبتنی بر metadata و اختلاف snapshot کافی باشد مگر DBA بررسی دقیق را درخواست کند.

### ۴.۵ تحلیل طراحی و استفاده از Index

**هدف:** فراهم‌کردن فهرست قابل‌فهم از ایندکس‌های موجود، کلیدها و ترتیب آن‌ها، ستون‌های INCLUDE، یکتا/constraint بودن، اندازه، پارتیشن، استفاده در queryها و هزینه نگه‌داری؛ سپس پیشنهاد ایجاد، بازطراحی، ادغام، بررسی بیشتر یا کاندید حذف.

**منابع شواهد:** تعریف index از catalog views؛ usage و operational statistics؛ Query Store و planهای workload؛ missing-index data؛ اندازه و partition stats؛ آمار restart و بازه مشاهده. Missing index suggestions فقط یکی از منابع است: آن‌ها پیش از اجرای query برآورد می‌شوند، ممکن است چند پیشنهاد مشابه بسازند، ترتیب کلید نهایی را تعیین نمی‌کنند و هزینه اندازه/نگه‌داری را کامل نمی‌سنجند [4].

**نمایش ساختار کلید:** برای هر index، key columns با ترتیب ASC/DESC، included columns، filter، uniqueness، نوع index، constraint وابسته، اندازه و جدول مالک نمایش داده شود. مقایسه similarity باید بر اساس جدول، نوع، ترتیب prefix کلیدها، filter و include انجام شود؛ شباهت ظاهری نام ملاک نیست. توصیه به ادغام باید همراه با توضیح تفاوت workload باشد.

**تحلیل کاندید ایجاد:** چند پیشنهاد مشابه روی یک جدول گروه‌بندی شوند. سامانه باید نشان دهد کدام query/plan آن را پشتیبانی می‌کند، تخمین فایده چیست، کدام indexهای موجود هم‌پوشان‌اند، هزینه write و فضای احتمالی چیست، و چه محدودیت‌هایی باقی است. تولید `CREATE INDEX` فقط به صورت اسکریپت پیش‌نمایش‌شده و نیازمند تأیید باشد. مستند Microsoft صراحت دارد که missing-index requests نسخه آماده اجرا نیستند و باید همراه با indexهای موجود بازبینی و در صورت نیاز ترکیب شوند [4] [5].

**کاندید حذف:** ایندکسی فقط زمانی وارد فهرست بررسی شود که در بازه مشاهده کافی استفاده کاربری ثبت نشده باشد، هزینه نگه‌داری یا فضا معنی‌دار باشد، وابستگی constraint/foreign key نداشته باشد، پوشش Query Store و planها بررسی شده باشد، و امکان بازگردانی تعریف وجود داشته باشد. شمارنده‌های `sys.dm_db_index_usage_stats` با restart موتور پاک می‌شوند؛ بنابراین زمان شروع SQL Server و مدت مشاهده باید کنار آمار نمایش داده شوند و «صفر استفاده از زمان startup» نباید به‌تنهایی دلیل حذف باشد [6].

**ایمنی اقدام:**

1. `PRIMARY KEY`, `UNIQUE`, constraint-owned، indexهای پشتیبان FK و ساختارهای ویژه به‌صورت پیش‌فرض از حذف خودکار خارج باشند. SQL Server برای indexهای ایجادشده توسط PRIMARY KEY و UNIQUE، مسیر حذف constraint را لازم می‌داند [7].
2. فهرست کاندیدها همراه با شواهد، سطح اطمینان، بازه مشاهده، restartها، Query Store coverage، مصرف فضای index و هزینه update نمایش داده شود.
3. ابتدا فقط تولید اسکریپت و امکان کپی ارائه شود؛ اجرای DDL در MVP غیرفعال باشد.
4. قابلیت «غیرفعال‌سازی آزمایشی» فقط در مرحله بعد و پس از بررسی اثر semantics، edition/version، ویژگی‌های constraint، قابلیت بازگردانی و برنامه maintenance بررسی شود؛ disable کردن همیشه rollback بی‌خطر نیست.
5. هر تغییر با تأیید دو مرحله‌ای یا نقش DBA، پنجره اجرا، محدودیت MAXDOP/ONLINE در صورت پشتیبانی، audit و اسکریپت rollback انجام شود.
6. پس از تغییر، همان workload و شاخص‌های قبل/بعد مقایسه و امکان rollback برجسته باشد.

Microsoft توصیه می‌کند استفاده index در گذر زمان پایش شود و ایندکس‌های بدون استفاده با توجه به مشخصات workload بررسی شوند؛ indexهای بیشتر، سربار INSERT/UPDATE/DELETE و فضای بیشتری ایجاد می‌کنند [5]. این توصیه مجوز حذف بر مبنای snapshot کوتاه نیست.

### ۴.۶ سایر سلامت‌های زیرساخت و پایگاه

در نسخه‌های بعدی می‌توان health backup/restore، وضعیت availability/replication، blocking/deadlock، wait statistics، وضعیت TempDB، growth transaction log و تغییرات configuration را اضافه کرد. هر منبع باید به ماژول مستقل با نرخ جمع‌آوری و مجوزهای روشن تبدیل شود. برای عملیات فیزیکی بررسی index، سطح scan و اثر آن باید محتاطانه انتخاب شود؛ DMV فیزیکی اطلاعات fragmentation و page count می‌دهد و روی readable secondary می‌تواند REDO را block کند، پس جمع‌آوری گسترده آن نیازمند برنامه‌ریزی است [8].

## ۵. موتور Insight و چرخه عمر پیشنهاد

هر Insight باید این فیلدها را داشته باشد:

- شناسه و نوع: anomaly, threshold, forecast, regression, recommendation.
- دامنه: instance/database/object/query/job/index/file.
- عنوان کوتاه و شدت.
- شرح ساده مسئله و پیامد محتمل.
- مقدار جاری، baseline، بازه و timestamp مشاهده.
- شواهد و لینک به query/run/object مرتبط.
- روش تشخیص یا forecast و فرض‌های آن.
- confidence و علت کاهش confidence.
- اقدام پیشنهادی، ریسک اقدام و پیش‌نیازها.
- وضعیت رسیدگی: جدید، بررسی‌شده، snoozed، اقدام برنامه‌ریزی‌شده، رفع‌شده، نادرست.
- مالک، زمان‌ها و سابقه تغییر وضعیت.
- نتیجه پیش/پس از اقدام برای یادگیری و سنجش اثربخشی.

چرخه پیشنهادی:

1. **دریافت:** ثبت منبع داده، موفقیت و زمان مشاهده.
2. **اعتبارسنجی:** کشف داده ناقص، reset counter، تغییر نسخه، timezone و gap.
3. **تشخیص:** قواعد شفاف برای آستانه‌های پایه و baselineهای زمان‌محور.
4. **اولویت‌بندی:** ترکیب شدت، احتمال، زمان تا اثر، دامنه و confidence؛ علت رتبه‌بندی قابل‌مشاهده باشد.
5. **ارائه:** کارت Insight با شواهد و next step مشخص.
6. **رسیدگی:** acknowledge، واگذاری، runbook یا ثبت اقدام DBA.
7. **ارزیابی:** مقایسه پس از اقدام و ثبت اینکه پیشنهاد مفید بود یا خیر.

AI/مدل زبانی، اگر بعداً افزوده شود، فقط می‌تواند توضیح را خلاصه کند یا شواهد را قابل‌خواندن‌تر کند. عددها، forecast و تصمیم حذف/ایجاد index باید از داده و الگوریتم قابل‌آزمون بیایند؛ مدل زبانی نباید بدون تأیید DDL اجرا کند.

## ۶. داشبورد پیشنهادی DBA

### نمای کلی

نمای Fleet/Instance با سلامت اتصال، alertهای مهم، موارد نزدیک به آستانه ظرفیت، Query regressionهای جدید، Jobهای overdue و تغییرات برجسته. هر کارت به جزئیات منبع و بازه باز شود.

### مرکز Insight

فهرست مرتب‌شده با فیلتر حوزه، severity، confidence، زمان، وضعیت رسیدگی و owner. پیش‌نمایش شواهد و پیشنهاد در همان صفحه و پیوند به Query/Job/Table/File/Index detail.

### جزئیات Query

تاریخچه runtime، planهای تغییرکرده، wait/CPU/I/O، فراوانی اجرا و ارتباط با ایندکس‌های پیشنهادی. متن query می‌تواند حساس باشد؛ نمایش با RBAC و redaction کنترل شود.

### جزئیات Job

Schedule و اجرای بعدی، سابقه اجرا، trend مدت، Step failureها، وابستگی‌ها و تشخیص دیرکرد. نسبت به baseline مشابه روز/ساعت توضیح داده شود.

### ظرفیت و رشد

فضای volume، اندازه فایل، used/free داخل فایل، autogrowth، رشد جدول و index، trend و افق پیش‌بینی. مقیاس هر نمودار و تفاوت storage allocated با volume free روشن باشد.

### Index Workbench

فهرست index با ترتیب کلید، include, filter, unique/constraint, usage window, reads/writes, size, overlap, query evidence. تب‌های جدا برای پیشنهاد ایجاد، ادغام/بازبینی، و کاندید حذف. هیچ‌یک نباید «خوب/بد» مطلق و بدون شرایط نشان داده شود.

## ۷. مجوز و امنیت

برای مشاهده metadata و performance DMVs ممکن است مجوزهای فراتر از SELECT روی `msdb` لازم باشد. هر metric باید مجوز موردنیاز و نسخه‌های سازگار را مستند کند. قابلیت‌های خواندن data plane از اقدام‌های تغییردهنده جدا شوند؛ credential جمع‌آوری نباید به‌طور پیش‌فرض مجوز ساخت/حذف index داشته باشد.

برای deployment شبکه‌ای، احراز هویت، نقش‌های viewer/operator/DBA/admin، HTTPS، audit و حفاظت secret الزامی است. متن query، plan و command ممکن است حاوی داده حساس باشد. exportها و logها باید redaction و کنترل دسترسی داشته باشند.

## ۸. نقشه راه پیشنهادی

### مرحله صفر: پایه اعتماد

اصلاح مشکلات صحت داشبورد موجود، وضعیت تازه‌بودن داده، collector health، چند تست پایه و تعریف contract داده. تا زمانی که منبع داده قابل اعتماد نباشد، forecasting به کاربر نشان داده نشود.

### مرحله یک: تاریخچه و Insightهای کم‌ریسک

ذخیره snapshotهای دوره‌ای، trend Jobها، وضعیت اجرای بعدی، رشد ساده file/table، Query Store read-only و alertهای threshold قابل توضیح. در این مرحله هیچ DDL یا عملیات تغییردهنده اجرا نشود.

### مرحله دو: Forecast و Index Workbench فقط‌خواندنی

افزودن forecastهای ساده با confidence و فرض‌های روشن؛ Query regression؛ تحلیل ساختار/هم‌پوشانی/استفاده index؛ تولید اسکریپت پیشنهادی بدون اجرای خودکار. بازه‌های کافی برای index usage الزامی باشد.

### مرحله سه: جریان کنترل‌شده اقدام

پس از RBAC و audit، اجرای اقدام‌های مجاز به‌صورت opt-in و تنها با تأیید DBA، پنجره نگه‌داری، پیش‌نمایش، rollback و اندازه‌گیری قبل/بعد بررسی شود. حذف index به‌صورت خودکار در scope محصول قرار نگیرد.

## ۹. معیارهای پذیرش

- هر Insight قابل بازتولید باشد: ورودی، بازه، rule/model version و دلیل نتیجه قابل مشاهده باشد.
- اگر داده ناکافی، reset شده یا stale باشد، forecast با اطمینان بالا ارائه نشود.
- زمان پیش‌بینی پرشدن فایل همراه با تاریخچه، نرخ رشد، آستانه و بازه عدم‌قطعیت باشد؛ فضای volume از فضای داخلی فایل جدا باشد.
- رشد جدول و index از snapshotهای زمان‌دار محاسبه شود و افزایش row count تقریبی به‌عنوان عدد قطعی برچسب نخورد.
- Query regression با مقایسه بازه/plan و metric مشخص شود، نه صرفاً با یک مدت مطلق.
- پیشنهاد missing index با indexهای موجود گروه‌بندی و duplicate/overlap احتمالی مشخص شود.
- کاندید حذف، مدت مشاهده و آخرین restart را نشان دهد؛ indexهای constraint/unique/primary key به‌طور پیش‌فرض قابل حذف نباشند.
- نسخه نخست هیچ `CREATE INDEX`, `DROP INDEX`, `ALTER INDEX`, force-plan یا اجرای Job را بدون اقدام صریح DBA انجام ندهد.
- اقدام تأییدشده دارای preview، audit، outcome، سنجه قبل/بعد و راه برگشت باشد.
- جمع‌آوری queryهای سنگین و physical stats محدود، زمان‌بندی‌پذیر و قابل توقف باشد.
- هر instance در صورت شکست جمع‌آوری جداگانه علامت‌گذاری شود و داده سالم سایر instanceها حفظ شود.
