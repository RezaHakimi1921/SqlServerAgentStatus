# سند نیازمندی از سمت مانوس

**موضوع:** بررسی محصول SqlServerAgentStatus، جریان جمع‌آوری داده و داشبوردها  
**تهیه‌کننده:** Manus AI  
**تاریخ بررسی:** ۱۶ نوامبر ۲۰۲۶  
**مبنای بررسی:** کد شاخه `main` در commit `f101544` و مستندات رسمی Redgate، Idera و Devart/dbForge

## ۱. نتیجه بررسی محصول فعلی

این پروژه یک برنامه دسکتاپ/محلی مبتنی بر Python و Dash برای دیدن وضعیت و تاریخچه SQL Server Agent است. داده‌ها مستقیم از `msdb` خوانده می‌شوند؛ برنامه داده‌ها را در مخزن تاریخی خودش ذخیره نمی‌کند. در نتیجه، آنچه نمایش داده می‌شود به موجودبودن تاریخچه در `msdb` و بازه‌های کوتاه واکشی برنامه وابسته است. این ابزار را باید در وضعیت فعلی «داشبورد عملیات SQL Agent برای یک اتصال» دانست، نه سامانه جامع پایش SQL Server یا سامانه هشداردهی مستقل.

سه نتیجه برای اولویت کار وجود دارد. نخست، نمودار Gantt در پیاده‌سازی کنونی عملاً خالی ساخته می‌شود، چون اجزای ردیف‌ها و محور زمان تولید شده‌اند اما به درخت خروجی اضافه نشده‌اند (`app.py` در تابع `render_gantt_chart`). دوم، عبارت «اجرای بعدی» در جدول وجود دارد ولی همیشه `—` نمایش داده می‌شود؛ زمان‌بندی از `sysjobschedules` و `sysschedules` خوانده نمی‌شود. سوم، مسیر تنظیمات رمز SQL در Windows Credential Manager نگه‌داری می‌کند که برای ابزار محلی مناسب است، اما دسترسی وب برنامه به‌طور کلی احراز هویت نشده و این طراحی فقط برای bind محلی قابل‌قبول است.

## ۲. جریان فعلی جمع‌آوری داده

### ۲.۱ راه‌اندازی و پیکربندی اتصال

برنامه تنظیمات را از `.env` می‌خواند (`config.py`). مقصد پیش‌فرض پایگاه `msdb`، بازه تازه‌سازی پیش‌فرض پنج دقیقه و bind پیش‌فرض `127.0.0.1:8050` است. رمز با `keyring` در Windows Credential Manager ذخیره می‌شود و کد مهاجرتی نیز رمز قدیمی موجود در `.env` را به آن منتقل می‌کند (`config.py`, `secrets_store.py`). در پنجره تنظیمات، اتصال آزمایش می‌شود و فقط در صورت موفقیت ذخیره می‌شود (`app.py`, callback `setup_feedback`). مستند نصب مجوزهای SELECT روی `sysjobs`, `sysjobsteps`, `sysjobhistory` و `sysjobactivity` را مثال می‌زند (`INSTALL.md`).

**نیازمندی پیشنهادی:** حساب سرویس/کاربر پایش باید کمترین مجوز لازم را داشته باشد. نصب باید قابلیت احراز اتصال، آزمون مجوز خواندن هر منبع، نمایش خطای قابل‌اقدام و اعتبارسنجی رمزنگاری ارتباط را فراهم کند. مقدارهای پیش‌فرض رمزنگاری باید امن باشند و انتخاب اعتماد به گواهی نامعتبر صریح و مستند باشد؛ اکنون گزینه‌های `Encrypt` و `TrustServerCertificate` از تنظیمات محیطی می‌آیند و پیش‌فرض فعلی `Encrypt=no` و `TrustServerCertificate=yes` است.

### ۲.۲ زمان‌بندی واکشی

یک `dcc.Interval` در مرورگر با فاصله پیکربندی‌شده فعال می‌شود. همان callback داده‌ها را هنگام بارگذاری اولیه، با دکمه بروزرسانی، و بر مبنای Interval واکشی می‌کند (`app.py`, `fetch_all_data`). توقف بروزرسانی، واکشی خودکار را متوقف می‌کند. «Snapshot» در عمل همان متوقف‌کردن واکشی و نگه‌داشتن داده‌های موجود در حافظه مرورگر است؛ این قابلیت ذخیره نسخه پایدار یا قابل‌بازیابی از وضعیت نیست.

**نیازمندی پیشنهادی:** وضعیت داده باید زمان آخرین واکشی موفق، زمان آخرین خطا و سن داده را نمایش دهد. توقف، snapshot و بروزرسانی دستی باید از نظر معنایی جدا باشند: توقف فقط polling را متوقف کند؛ snapshot باید در صورت نیاز نسخه مشخصی را ذخیره یا نام‌گذاری کند؛ refresh دستی باید درخواست تازه را از cache عبور دهد. اگر چند کاربر یا چند نمونه برنامه اجرا شوند، polling سمت مرورگر موجب چندبارخوانی از SQL Server می‌شود؛ برای مقیاس چندکاربره زمان‌بندی مرکزی سمت سرور/worker مناسب‌تر است.

### ۲.۳ پرس‌وجوها و منابع داده

`db.py:get_running_jobs` وضعیت جاری را از `msdb.dbo.sysjobactivity` با آخرین `session_id` می‌خواند و فقط سطرهای دارای `start_execution_date` و بدون `stop_execution_date` را در حال اجرا می‌داند. `get_dashboard_batch` در یک اتصال SQL این بسته را واکشی می‌کند:

- فهرست Jobها و فعال/غیرفعال‌بودن از `msdb.dbo.sysjobs`.
- آخرین نتیجه هر Job در بازه اخیر از سطرهای outcome یعنی `sysjobhistory.step_id = 0`؛ بازه فعلی یک روز است.
- میانگین مدت پنج اجرای موفق اخیر هر Job؛ محاسبه در SQL Server انجام می‌شود.
- حداکثر ۲۴ اجرای امروز برای هر Job، برای Gantt.
- حداکثر ۵۰ failure مربوط به Stepهای امروز و آخرین failure هر Job در بازه اخیر؛ متن پیام به ۵۰۰ نویسه محدود شده است.

خروجی batch برای هشت ثانیه در حافظه process cache می‌شود (`db.py`, `_BATCH_CACHE`). وضعیت running جداگانه و بدون این cache خوانده می‌شود. بنابراین در refresh عادی همه پرس‌وجوهای batch ممکن است از cache هشت‌ثانیه‌ای پاسخ بگیرند؛ دکمه refresh cache را invalid می‌کند. پنجره جزئیات Job هنگام بازشدن دو پرس‌وجوی جدا برای تعریف Stepها از `sysjobsteps` و تاریخچه گروه‌بندی‌شده اجراها از `sysjobhistory` می‌فرستد. حداکثر ۲۰ اجرا نشان داده می‌شود و تاریخچه برای این modal محدودیت روز ندارد.

**نیازمندی پیشنهادی:** هر پرس‌وجو باید نام منبع، زمان اجرا، تعداد ردیف و زمان پاسخ را ثبت کند؛ خطای هر بخش نباید بی‌دلیل کل داشبورد را از داده تازه محروم کند. cache باید با کلید اتصال/سرور و بازه زمانی تعریف شود، TTL و سیاست invalidation مشخص داشته باشد و قابل مشاهده باشد. تنظیم بازه تاریخچه و سقف نتایج بهتر است در تنظیمات مدیریتی باشد. برای چند سرور، مدل `Instance → Job → Run → Step` با شناسه یکتا و برچسب سرور اضافه شود.

### ۲.۴ تبدیل و نگه‌داری موقت داده

داده‌های SQL در `app.py` به ساختارهای ساده تبدیل می‌شوند و `datetime` به ISO string سریال می‌شود. Callbackهای ادغام، run جاری را با آخرین outcome ترکیب می‌کنند، میانگین موفقیت را برای تخمین progress می‌گیرند و داده‌های Gantt را می‌سازند (`calculations.py`). بخش عمده وضعیت در `dcc.Store` مرورگر قرار می‌گیرد؛ پایگاه داده تاریخی برنامه وجود ندارد.

**نیازمندی پیشنهادی:** قرارداد خروجی هر query باید نسخه‌دار و تست‌پذیر باشد. زمان‌ها باید timezone/منطقه زمانی SQL Server را روشن کنند و تبدیل زمان‌ها با تاریخچه‌های نیمه‌شب و اجرای عبوری از روز آزموده شود. داده تاریخی برای تحلیل روند باید در repository مجزا با retention، پاکسازی و محدودیت حجم ذخیره شود؛ نگه‌داری بی‌پایان داده در `msdb` جایگزین این کار نیست.

## ۳. بررسی جزءبه‌جزء داشبوردها

### ۳.۱ سربرگ و کنترل‌های عمومی

سربرگ وضعیت زنده، Snapshot، توقف/ادامه، اعلان‌ها، تنظیمات و بروزرسانی دستی دارد (`app.py`, layout). نمایش زنده بودن فعلی بیشتر یک نشانگر UI است و زمان موفقیت آخرین poll را اثبات نمی‌کند. عنوان اعلان‌ها به خطاهای امروز اشاره می‌کند و داده failure از queryهای امروز ساخته می‌شود.

**نیازمندی:** نشانگر «متصل/قطع/قدیمی» باید بر مبنای نتیجه آخرین query باشد. کنار اعلان‌ها تعداد خطای جدید، زمان وقوع، سرور و نام Job دیده شود؛ مشاهده/بستن اعلان نباید خطا را از تاریخچه حذف کند. خطاهای تکراری باید deduplicate و قابل acknowledge باشند.

### ۳.۲ تب فهرست Jobها و کارت‌های آماری

فهرست شامل نام و دسته‌بندی تخمینی Job، وضعیت، progress، مدت، اجرای بعدی، و دکمه جزئیات است. فیلتر وضعیت، جستجوی نام و صفحه‌بندی ۱۵تایی سمت برنامه وجود دارد. کارت‌های وضعیت و فیلتر از داده overview ساخته می‌شوند. دسته‌بندی بر اساس نقطه و زیرخط نام Job حدس زده می‌شود و taxonomy رسمی نیست.

**یافته‌ها:** ستون اجرای بعدی مقدار واقعی ندارد و همه‌جا `—` است (`build_jobs_overview`). درصد اجرای Job تاریخی یا نمایشی است، نه میزان پیشرفت واقعی Stepها. برای اجرای جاری درصد از میانگین اجراهای موفق اخیر برآورد می‌شود؛ اگر آمار موفق وجود نداشته باشد، صفر درج می‌شود. این مقدار ممکن است با پیشرفت واقعی اشتباه گرفته شود. `run_status=2` در کد با وضعیت شکست‌خورده نمایش داده شده است، در حالی که در تاریخچه SQL Agent وضعیت ۲ retry است؛ نمایش retry به‌عنوان شکست نهایی معنای دقیقی ندارد. Job غیرفعال با وضعیت `idle` آمده و از Job فعالِ بی‌سابقه جدا نیست.

**نیازمندی:** وضعیت‌ها باید مدل جداگانه و مستند داشته باشند: Running, Succeeded, Failed, Retry, Canceled, Disabled, No history, Unknown. Progress باید با عنوان «برآورد بر پایه میانگین» مشخص شود یا به‌صورت پیش‌فرض به‌جای درصد مدت سپری‌شده نمایش داده شود. زمان شروع، مدت اجرای جاری، زمان آخرین موفقیت، نتیجه آخرین اجرا، تعداد شکست‌ها در بازه و زمان اجرای بعدی باید فیلتر و مرتب‌سازی شوند. جستجو بهتر است server-side انجام شود، تا فهرست حجیم کامل به مرورگر منتقل نشود.

### ۳.۳ جزئیات Job

با کلیک روی دکمه هر Job، دو پرس‌وجوی جزئیات اجرا می‌شوند. پنجره خلاصه وضعیت فعلی، زمان و مدت آخرین اجرا، نتیجه و تعداد Stepها را می‌دهد. آخرین اجرا با وضعیت/مدت و پیام Stepها دیده می‌شود؛ اجراهای قبلی تا ۲۰ مورد با جزئیات Step قابل بازشدن هستند. تعریف Job از `sysjobsteps` شامل نام، نوع subsystem و پیش‌نمایش command تا ۲۰۰ نویسه است. برای runهای گروه‌بندی‌شده، کد از `instance_id` outcomeها برای یافتن سطرهای Step بین دو outcome استفاده می‌کند.

**نیازمندی:** modal باید لینک روشن به آخرین اجرا/آخرین failure داشته باشد و امکان تغییر بازه و صفحه‌بندی تاریخچه فراهم کند. commandهای Job می‌توانند اطلاعات حساس داشته باشند؛ نمایش command باید قابل‌تنظیم و مبتنی بر مجوز باشد. مدت اجرای SQL Agent با دقت محدودیت قالب تاریخی `run_duration` تفسیر شود. وضعیت هر Step و اجرای نهایی از هم تفکیک شوند و retry/cancel صریح باشند. خطای دسترسی تاریخچه باید با خطای اتصال کل سامانه اشتباه نشود.

### ۳.۴ تب Gantt روزانه

`calculations.py:build_gantt_rows` اجرای امروز را از تاریخچه می‌گیرد و با وضعیت running ترکیب می‌کند؛ محور مورد نظر ۲۴ ساعت است، فیلتر status و zoom بین ۴۰ تا ۲۰۰ درصد وجود دارد. داده امروز از query حداکثر ۲۴ اجرای هر Job می‌آید.

**ایراد بحرانی:** `render_gantt_chart` اجزای محور، grid، برچسب‌ها و `gantt_row_els` را تولید می‌کند، اما خروجی `chart` عملاً با children خالی ساخته می‌شود. بنابراین Gantt خالی است، حتی در صورت وجود داده. علاوه بر آن، اجرای طولانی عبوری از نیمه‌شب حذف یا ناقص می‌شود، چون ساخت ردیف‌ها فقط اجراهایی را می‌پذیرد که تاریخ شروعشان امروز است و محور فقط یک روز را پوشش می‌دهد. آزمون‌های repository برای پوشش این جریان یافت نشدند.

**نیازمندی:** ابتدا خروجی chart باید با label-column، timeline، grid، now-marker و ردیف‌های bars ساخته شود و تست رندر/داده اضافه گردد. اجرای عبوری از روز باید در ابتدا/انتهای محور بریده شود، نه حذف. لازم است timezone و مرز روز سرور مشخص باشد. Gantt باید اجرای پرتکرار، هم‌زمانی، retry و اجرای بیش از ۲۴ بار را به‌درستی نمایش دهد؛ محدودیت ۲۴ باید قابل تنظیم یا صفحه‌بندی شود. بارهای کلیک‌پذیر باید به جزئیات اجرای مشخص باز شوند.

### ۳.۵ اعلان‌ها و خطاها

پنل اعلان‌ها و badge بر اساس `today_failures` ساخته شده‌اند و پنل به خطاهای Stepهای امروز متکی است. query جداگانه آخرین failure هر Job نیز در overview استفاده می‌شود. در کد فعلی شواهدی از ارسال ایمیل، webhook، Slack/Teams، escalation یا قواعد alert مستقل دیده نمی‌شود؛ اعلان داخل برنامه معادل هشدار عملیاتی خارج از مرورگر نیست.

**نیازمندی:** قواعد هشدار قابل تنظیم بر مبنای نتیجه job، مدت بیش از حد، عدم اجرا در موعد، failure پیاپی و تأخیر زمان‌بندی‌شده تعریف شود. کانال‌های ایمیل و webhook و سیاست quiet hours، retry، deduplication، acknowledge و escalation نیاز است. هر هشدار باید شامل نام instance، job، زمان، step/message و deep link باشد. این قابلیت به‌عنوان کارکرد جدید تعریف می‌شود، نه قابلیتی که اکنون موجود است.

### ۳.۶ تنظیمات و امنیت

تنظیمات شامل server/database/user/password/driver و فاصله refresh است. تغییر اتصال از درخواست محلی مجاز است (`_is_local_request`). این کنترل فقط callback ذخیره تنظیمات را محدود می‌کند و جایگزین احراز هویت برای دسترسی به کل برنامه نیست. bind پیش‌فرض `127.0.0.1` خطر دسترسی شبکه‌ای را محدود می‌کند؛ اگر `DASH_HOST` به آدرس عمومی تغییر داده شود، برنامه باید پشت احراز هویت و HTTPS قرار گیرد. مقادیر SQL exception مستقیماً در UI نمایش داده می‌شوند و لازم است از نشت جزئیات اتصال جلوگیری شود.

**نیازمندی:** برای حالت تک‌کاربره bind محلی به‌عنوان پیش‌فرض حفظ شود. هر پشتیبانی از شبکه باید با login/role، session امن، HTTPS و CSRF protection همراه باشد. رمز و command حساس log نشوند. تنظیمات رمزنگاری، چرخش credential و حذف credential تعریف شود. دسترسی خواندن اطلاعات `msdb` نیز به حداقل لازم محدود بماند.

## ۴. مقایسه با محصولات شناخته‌شده

### Redgate Monitor

مستند Redgate می‌گوید Base Monitor به‌صورت پیوسته metricها و alertهای ازپیش‌تعریف‌شده را از سلسله‌مراتب سرور، ماشین، instance، database و job نمونه‌برداری می‌کند؛ منابع شامل PerfMon/WMI، DMVها، آمار wait، داده backup، وضعیت سرویس و اطلاعات پیکربندی است. قواعد alert در سطح کلی و سطوح پایین‌تر قابل تنظیم و ارث‌بری هستند. صفحه Jobs تعداد اجراها را در بازه روز/هفته/ماه جمع‌بندی می‌کند و فهرست آخرین jobهای موفق/ناموفق با drill-down دارد [1] [2].

**درس کاربردی برای این پروژه:** تعریف منظم metric و alert، roll-up چند سرور، روند تاریخی و امکان drill-down. دامنه فعلی SqlServerAgentStatus فقط Agent jobs است و نباید بدون افزودن collectorهای دیگر با Redgate به‌عنوان SQL performance monitor مقایسه شود.

### Idera SQL Diagnostic Manager

مستند معماری Idera چهار بخش اصلی را توصیف می‌کند: Collection Service برای جمع‌آوری زمان‌بندی‌شده و on-demand، Management Service برای ارتباط با کنسول و ذخیره داده، Repository مرکزی SQL Server برای metrics/history/alerts/configuration، و Console/Web Console برای نمایش داده زنده و تاریخی [3]. قابلیت‌های رسمی کنونی محصول همچنین پایش زنده، alert، تحلیل query/wait/blocking/deadlock، گزارش estate، baseline، پیش‌بینی ظرفیت و نگه‌داری تاریخچه را معرفی می‌کند [4].

**درس کاربردی:** جداسازی collector از UI، repository مرکزی و تفکیک live view از history. این معماری مقیاس‌پذیرتر از polling مستقیم از callback مرورگر است؛ برای پروژه فعلی مرحله بعدی باید ابتدا چند instance و ذخیره تاریخچه را اضافه کند، نه اینکه یکباره همه قابلیت‌های محصول سازمانی را تقلید کند.

### dbForge Monitor از Devart

صفحه رسمی dbForge Monitor آن را افزونه رایگان SSMS برای پایش real-time عملکرد SQL Server، وضعیت server/database، CPU، memory و تشخیص query کند معرفی می‌کند [5]. مستند رسمی صریحاً می‌گوید ابزار داده را log نمی‌کند و فقط وضعیت جاری را برای پایش real-time نشان می‌دهد [6].

**درس کاربردی:** طراحی سبک و real-time برای دیدن وضعیت لحظه‌ای مناسب است؛ اما نبود history محدودیت تحلیل پس از رخداد است. پروژه حاضر نیز در حال حاضر به ذخیره داخلی تاریخچه پایش مجهز نیست، ولی از تاریخچه محدود `msdb` استفاده می‌کند؛ پس برای گزارش trend و incident forensics به repository جدا نیاز دارد.

## ۵. نیازمندی‌های پیشنهادی محصول

### اولویت صفر — اصلاح صحت و اعتمادپذیری

1. اصلاح رندر Gantt و اضافه‌کردن تست برای اجرای موفق، ناموفق، running، چند اجرای یک Job، حالت بدون داده و عبور از نیمه‌شب.
2. تصحیح mapping وضعیت‌های SQL Agent؛ retry نباید failure نهایی نامیده شود و canceled/disabled/no-history از هم جدا باشند.
3. افزودن تست واحد برای تبدیل تاریخ/مدت، محاسبه progress، گروه‌بندی Stepها و محاسبه مرز روز.
4. نمایش زمان آخرین واکشی موفق و stale/error در UI؛ پیام اتصال و مجوزها واضح و بدون افشای secret باشد.
5. اصلاح مستندات نام repository/مسیر clone و متغیرهای refresh، چون `README.md` و `INSTALL.md` فعلی به نام‌های متفاوت/قدیمی اشاره می‌کنند.

### اولویت یک — ارزش عملیاتی برای SQL Agent

1. پشتیبانی از چند SQL Server با برچسب instance و فیلتر/گروه.
2. خواندن زمان اجرای بعدی از scheduleهای فعال Agent و نمایش «عدم زمان‌بندی» به‌جای خط تیره مبهم.
3. هشدارهای قابل تنظیم برای شکست، تأخیر/عدم اجرا، اجرای طولانی و تکرار failure؛ ابتدا email و webhook.
4. فیلتر، مرتب‌سازی و جستجوی server-side بر روی status، owner/category، زمان آخرین اجرا و بازه تاریخی.
5. صفحه تاریخچه با بازه انتخابی، صفحه‌بندی، شمارش موفقیت/شکست و روند مدت اجرا؛ تفکیک نتیجه Job و نتیجه Step.
6. نمایش حدود داده: آخرین refresh، بازه history، محدودیت retention در SQL Agent و زمان/منطقه زمانی سرور.

### اولویت دو — معماری و قابلیت رشد

1. افزودن collector/worker سمت سرور با تنظیم برنامه‌ریزی‌شده؛ UI فقط API را مصرف کند.
2. repository تاریخی با retention و partition/پاکسازی برای داده‌های run/step/alert و metricهای انتخاب‌شده.
3. مدیریت سلامت collector، وضعیت آخرین poll برای هر instance، backoff و retry اتصال و صف خطا.
4. احراز هویت/نقش‌ها و ثبت audit برای هر نوع deployment غیرمحلی.
5. گزارش و export CSV، اعلان چندکاناله و داشبورد خلاصه fleet.
6. پس از تثبیت هسته Agent، در صورت نیاز واقعی، جمع‌آوری CPU، حافظه، I/O، waits، blocking و queryهای پرهزینه به‌عنوان ماژول‌های جداگانه تعریف شود؛ این دامنه با ابزار صرفاً Agent یکی نیست.

## ۶. طرح پیشنهادی جریان هدف

`SQL Server instances` ← حساب read-only و connection policy امن ← `Collector مرکزی` (poll زمان‌بندی‌شده، timeout، retry، سلامت) ← `Normalization/validation` (timezone/status/شناسه و deduplication) ← `Repository تاریخی` (runs, steps, alerts, snapshots, retention) ← `API` (فیلتر/صفحه‌بندی/تجمیع) ← `Dashboard و اعلان‌ها`.

Collector باید بتواند خطای یک instance را مستقل از بقیه ثبت کند. UI باید از API وضعیت آخرین بار موفق و عمر داده را بگیرد. قواعد alert باید از داده نرمال‌شده و history تغذیه شوند، نه از شمارش لحظه‌ای در مرورگر. داده خام حساس مانند commandهای Job فقط با مجوز مناسب قابل نمایش باشد.

## ۷. معیارهای پذیرش پیشنهادی

- برای نمونه داده آزمون که دربردارنده همه statusهای SQL Agent است، فیلترها و برچسب‌ها دقیق و بدون تبدیل retry به failure نهایی عمل کنند.
- Gantt برای اجرای امروز خروجی ردیف/محور واقعی بسازد و اجرای عبوری از نیمه‌شب را در مرز روز clip کند.
- اجرای بعدی برای Jobهای زمان‌بندی‌شده از schedule خوانده شود؛ Job بی‌برنامه مقدار معنایی روشن داشته باشد.
- قطع دسترسی به یک instance، اطلاعات سایر instanceها را از دسترس خارج نکند و خطای همان instance قابل تشخیص باشد.
- زمان آخرین poll موفق و عمر داده در داشبورد دیده شود؛ refresh ناموفق نباید به‌صورت داده زنده معرفی شود.
- قواعد failure و overdue با تست قابل بازتولید باشند و اعلان تکراری در پنجره deduplication تولید نشود.
- برای deployment غیرمحلی، دسترسی ناشناس به داشبورد و تنظیمات ناممکن باشد.
- تست‌های CI تبدیل‌ها، query/result mapping و callbackهای اصلی را اجرا کنند.

## ۸. ارزیابی کوتاه ریسک‌ها

ریسک بالای محصول فعلی، نمایش نادرست Gantt و وضعیت‌هاست؛ این‌ها روی برداشت کاربر از رخداد اثر می‌گذارند. ریسک بعدی قدیمی‌بودن داده در زمان خطای اتصال و نبود نشانگر شفاف freshness است. نبود تاریخچه اختصاصی و alert خارجی باعث می‌شود محصول برای تحلیل روند یا اطلاع‌رسانی هنگام بسته‌بودن مرورگر مناسب نباشد. پیکربندی bind محلی، نبود احراز هویت سراسری را در استفاده روی همان دستگاه قابل‌قبول‌تر می‌کند، اما تغییر bind به شبکه باید یک مرز امنیتی تلقی شود.
