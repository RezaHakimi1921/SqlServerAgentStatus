# نقشه راه توسعه با هوش مصنوعی

**موضوع:** راهنمای مرحله‌ای توسعه SqlServerAgentStatus برای AI توسعه‌دهنده
**تهیه‌کننده:** Manus AI
**تاریخ:** ۱۶ نوامبر ۲۰۲۶
**هدف:** تعیین اسناد مرجع، ترتیب اجرا، خروجی هر مرحله و مرزهای ایمنی برای توسعه با کمک AI

## ۱. روش استفاده از این نقشه

AI توسعه‌دهنده باید پیش از تغییر کد این سند و اسناد مرتبط را بخواند، وضعیت واقعی repository و branch را بررسی کند و فقط مرحله‌ای را اجرا کند که کارفرما/مسئول پروژه درخواست یا تأیید کرده است. این نقشه مجوز اجرای همه قابلیت‌ها یا تغییر محیط production نیست.

هر مرحله باید در تغییر کوچک و قابل بازبینی پیاده شود. AI باید قبل از پیاده‌سازی، فایل‌ها و تست‌های مرتبط را بخواند؛ تغییر را با ساختار موجود سازگار کند؛ تست اجرا کند؛ نتیجه و موارد اجرا‌نشده را صریح بگوید؛ و تغییرات خارج از scope را وارد نکند.

اگر سند و کد با هم تعارض دارند، ابتدا کد فعلی را واقعیت وضعیت موجود بدان، سند نیازمندی را هدف محصول بدان، و تعارض material را در گزارش مرحله ثبت کن. تصمیم معماری جدید را بدون توضیح و ثبت ADR وارد نکن. اطلاعات credential یا داده واقعی مشتری را در تست، log، issue یا commit قرار نده.

## ۲. اسناد مرجع و زمان استفاده

### اسناد موجود در `docs/`

1. **`docs/سند نیازمندی از سمت مانوس.md`** — مرجع شناخت محصول فعلی، جمع‌آوری داده، مسیر داشبوردها، یافته‌های کد، benchmarkهای Redgate/Idera/dbForge و نیازمندی‌های پایه. AI باید این سند را برای اصلاحات فعلی UI، Jobها، Gantt، اتصال و رفتار موجود بخواند.
2. **`docs/سند قابلیت‌ها.md`** — کاتالوگ قابلیت‌های قابل‌افزودن، کاربرد، مسیر فنی پیشنهادی و اولویت. AI از آن برای انتخاب دامنه بعد از تثبیت پایه استفاده کند و قابلیت را فقط به دلیل وجود در فهرست پیاده نکند.
3. **`docs/سند اینسایت و پیش‌بینی DBA.md`** — مرجع رفتار محصول برای Insight، پیش‌بینی، حوزه Query/Job/دیسک/رشد/index، شواهد، confidence، چرخه رسیدگی و ایمنی اقدام. هر طراحی analytics و پیشنهاد DBA باید با این سند سازگار باشد.
4. **`docs/سند معماری و پیاده‌سازی بک‌اند اینسایت.md`** — مرجع معماری هدف، ماژول‌بندی، موجودیت‌ها و schema منطقی، cadence، API، امنیت، الگوریتم MVP، تست و ترتیب فنی. AI برای تغییرات backend/collector/repository/forecast باید این سند را به‌عنوان specification اجرایی بخواند.
5. **`docs/نقشه راه توسعه با هوش مصنوعی.md`** — همین سند؛ مرجع ترتیب فازها، gateها و handoff توسعه.

### اسناد ریشه repository

- `README.md`: معرفی و راه‌اندازی سریع؛ هر تغییر پیکربندی یا تجربه نصب باید مستندات دو زبانه/زبان‌های موجود را هماهنگ کند.
- `INSTALL.md`: نصب، وابستگی‌ها، مجوز SQL و troubleshooting؛ هر نیازمندی ODBC/Python/permission جدید باید اینجا ثبت شود.
- `.env.example`: کلیدها و defaultهای مجاز؛ secret واقعی هرگز در این فایل درج نشود.
- `requirements.txt`: dependencyهای Python؛ فقط با دلیل فنی و بررسی سازگاری تغییر کند.
- کد واقعی `app.py`, `db.py`, `config.py`, `calculations.py`, `secrets_store.py`, `assets/` و `scripts/`: رفتار فعلی و نقاط ورود عملیاتی. AI نباید فرض کند شرح سند جای کد را می‌گیرد.

## ۳. سلسله‌مراتب تصمیم‌گیری

برای پیاده‌سازی، ترتیب مرجع چنین است:

1. محدودیت‌های ایمنی این سند: هیچ DDL/DML تغییردهنده روی SQL Server تحت پایش بدون scope و مجوز صریح اجرا نشود.
2. رفتار کد و پیکربندی فعلی برای فهم اثر regression.
3. نیازمندی‌های «سند نیازمندی از سمت مانوس» و «سند اینسایت و پیش‌بینی DBA» برای رفتار هدف.
4. «سند معماری و پیاده‌سازی بک‌اند اینسایت» برای طراحی فنی.
5. «سند قابلیت‌ها» برای انتخاب قابلیت‌های آینده.
6. تصمیم‌های جدید فقط با ثبت دلیل در ADR یا همین اسناد پس از تأیید مالک محصول.

هیچ AI نباید اسناد را به‌عنوان اجازه تغییر credential، اتصال به production، اجرای DDL یا انتشار خودکار تفسیر کند. اگر یک feature بدون تصمیم کارفرما انتخاب نمی‌شود—مانند DB repository، authentication، cloud deployment یا action execution—آن را به‌صورت گزینه و تصمیم باز گزارش کن.

## ۴. فازبندی توسعه

### فاز 0 — شناخت کد و خط مبنا

**اسناد لازم:** همه اسناد بالا، با تمرکز بر سند نیازمندی و سند معماری.
**کارها:** بررسی branch/status، ساختار، نسخه وابستگی‌ها، entry point و تست‌های موجود. اجرای تست/build موجود و ثبت baseline. شناسایی interfaceهای فعلی و تصمیم‌های باز.
**خروجی:** خلاصه وضعیت واقعی، فهرست ریسک‌های کد، برنامه کوچک برای فاز بعد.
**Gate:** هیچ تغییر ساختاری بزرگ پیش از فهم مسیر فعلی انجام نشود؛ تست‌های پایه و خطاهای پیش‌موجود از تغییرهای جدید جدا ثبت شوند.

### فاز 1 — صحت و اعتماد داشبورد فعلی

**اسناد لازم:** سند نیازمندی، بخش اولویت صفر و بررسی dashboard؛ README/INSTALL.
**کارها:** اصلاح Gantt به‌همراه تست؛ تصحیح mapping وضعیت retry/cancel/disabled/no-history؛ freshness و نمایش خطای source؛ رفع تفاوت مستندات repository/refresh؛ تست محاسبات زمان و مرز روز.
**خروجی:** داشبوردی که وضعیت‌ها را درست و قابل‌اعتماد نشان دهد، تست regression و مستندات به‌روز.
**Gate:** fixtureهای موفق/ناموفق/running/retry/بدون تاریخچه/عبور از نیمه‌شب پاس شوند. هیچ قابلیت بزرگ جدید در این فاز مخلوط نشود.

### فاز 2 — تصمیم و زیرساخت داده تاریخی

**اسناد لازم:** سند معماری، بخش schema/collection cadence/security؛ سند Insight، بخش model/data flow؛ README/INSTALL.
**کارها:** پیش از coding، ADR برای repository technology، single/multi-server، deployment model و retention ثبت شود. تعریف repository interface و migrations؛ ثبت `collection_run` و poll health؛ idempotent storage؛ secret reference و instance identity.
**خروجی:** migration قابل برگشت در محیط test، repository abstraction و تست persistence.
**Gate:** هیچ telemetry در دیتابیس production تحت پایش نوشته نشود مگر جداگانه تصویب شده باشد؛ backup، migration/rollback و retention تصمیم روشن داشته باشند.

### فاز 3 — Collector مستقل و telemetry پایه

**اسناد لازم:** سند معماری، cadence، adapter و failure isolation؛ سند Insight برای حوزه‌های هدف؛ INSTALL برای مجوزها.
**کارها:** انتقال polling از callback UI به collector قابل اجرا؛ query adapters با timeout و parameterization؛ ثبت poll status؛ backoff و per-instance isolation؛ شروع با SQL Agent و connection health. سپس schedule و file/object snapshots اضافه شوند.
**خروجی:** collector read-only، health status در UI/API، integration tests یا fixtures معتبر و راهنمای مجوز.
**Gate:** قطع یک instance، سایر داده‌ها را از دسترس خارج نکند؛ UI داده stale را live نشان ندهد؛ load queryها اندازه‌گیری شود.

### فاز 4 — Insight engine و پیش‌بینی توضیح‌پذیر

**اسناد لازم:** سند Insight، بخش اصول و چرخه lifecycle؛ سند معماری، بخش الگوریتم‌ها/schema/quality؛ سند قابلیت‌ها برای baseline و alert.
**کارها:** ابتدا ruleهای ساده و deterministic؛ baseline مدت Job؛ overdue/repeated failure؛ روند file/object size؛ minimum sample rules، confidence و data gaps؛ ذخیره Insight و evidence؛ deduplication و lifecycle.
**خروجی:** Insightهای قابل‌بازتولید با evidence، explanation، confidence و API read-only.
**Gate:** synthetic tests برای outlier، gap، restart، کمبود نمونه و تغییر ساختاری پاس شوند؛ forecast بدون کفایت داده باید «غیرقابل پیش‌بینی» اعلام شود. AI/LLM نباید اعداد forecast را جعل یا DDL تولید و اجرا کند.

### فاز 5 — Query Store و تحلیل workload

**اسناد لازم:** سند Insight حوزه Query؛ سند معماری Query Store adapter و permissions؛ INSTALL؛ منابع رسمی لینک‌شده در سند معماری.
**کارها:** وضعیت فعال‌بودن Query Store و سازگاری SQL Server بررسی شود؛ جمع‌آوری read-only و opt-in؛ تشخیص queryهای regression بر اساس بازه و plan/resource؛ نگه‌داری محدود metadata؛ صفحه جزئیات query با RBAC/redaction.
**خروجی:** رتبه‌بندی قابل توضیح و link به plan/metric؛ راهنمای permission و impact.
**Gate:** عدم دسترسی یا Query Store خاموش باید graceful باشد؛ متن query حساس به‌صورت پیش‌فرض افشا یا log نشود؛ plan change به‌تنهایی alert performance محسوب نشود.

### فاز 6 — Index Workbench فقط‌خواندنی

**اسناد لازم:** سند Insight، بخش Index؛ سند معماری، فصل Index safety؛ سند نیازمندی و منابع Microsoft؛ سند قابلیت‌ها.
**کارها:** catalog key/order/include/filter/unique/constraints؛ size و usage snapshots با restart detection؛ overlap detection explainable؛ missing-index grouping؛ کاندیدهای بررسی و confidence پایین در پوشش ناکافی.
**خروجی:** فهرست evidence-based با دلایل، بازه مشاهده، dependency flags و اسکریپت پیشنهادی برای review فقط در صورت درخواست.
**Gate:** هیچ indexی خودکار حذف/ساخته/غیرفعال نشود؛ PK/unique/constraint/FK-linked از حذف ساده خارج باشند؛ usage صفر بعد از restart کافی برای توصیه حذف نباشد. تست‌های ایمنی باید نبود DDL در مسیر read-only را اثبات کنند.

### فاز 7 — Insight Center، feedback و اعلان

**اسناد لازم:** سند Insight چرخه رسیدگی/داشبورد؛ سند قابلیت‌ها هشدار و incident center؛ سند معماری API/notifications/security.
**کارها:** UI فیلترشونده برای severity/confidence/source/freshness؛ acknowledge/assign/feedback؛ email/webhook با retry، dedup و audit؛ report.
**خروجی:** مرکز Insight و اعلان قابل ردیابی.
**Gate:** ارسال تکراری مهار شود؛ گیرنده/secret دسترسی محدود داشته باشد؛ شکست تحویل ثبت شود؛ UI از API مجاز تغذیه کند.

### فاز 8 — چندسروره، RBAC و مقیاس‌پذیری

**اسناد لازم:** سند معماری استقرار/API/security؛ سند قابلیت‌ها multi-instance؛ سند Insight permission.
**کارها:** instance registry و grouping؛ worker concurrency و queue/scheduler؛ user roles؛ health per-instance؛ retention/partition/backup؛ server-side pagination.
**خروجی:** rollout و migration چند instance، گزارش ظرفیت collector/repository و runbook.
**Gate:** performance/load test، failure isolation، access-control tests، secret rotation و recovery test پاس شوند.

### فاز 9 — اقدام کنترل‌شده (تنها با تأیید جداگانه)

**اسناد لازم:** سند Insight ایمنی اقدام؛ سند معماری Action service/security؛ ADR و مجوز روشن مالک محصول.
**کارها:** اگر صریحاً تصویب شد، Action API جدا با credential نوشتنی مستقل، RBAC، تأیید دوباره target، preview، maintenance window، audit، timeout، rollback و before/after metrics طراحی شود. شروع با یک action کم‌ریسک و محیط آزمایشی.
**خروجی:** قابلیت opt-in و محدود با runbook/rollback.
**Gate:** بدون تأیید صریح، این فاز اجرا نشود. حذف index یا اجرای DDL نباید در collector یا analytics engine قرار گیرد. استقرار production نیازمند تأیید انسانی و برنامه تغییر سازمانی است.

## ۵. قواعد کاری برای AI توسعه‌دهنده

- قبل از هر تغییر، `git status`, branch و آخرین commit را بخوان و تغییرات موجود کاربر را دست‌نخورده نگه دار.
- فقط scope یک فاز/issue را پیاده کن؛ بهینه‌سازی unrelated، refactor کامل یا اضافه‌کردن capability فهرست‌شده بدون درخواست انجام نده.
- اول تست یا fixture برای رفتار موردنظر بساز، سپس کد را تغییر بده.
- برای SQL از parameterها استفاده کن؛ identifierها را از input کاربر concatenate نکن. queryها باید با source/database مشخص، timeout و سقف load همراه باشند.
- credential و داده واقعی production را درخواست/چاپ/commit نکن. تست‌ها از fixture/synthetic data استفاده کنند.
- dependency جدید فقط با justification و بررسی license/compatibility اضافه شود. نسخه و نصب را در فایل‌های مرتبط مستند کن.
- migrationها versioned، تکرارپذیر و همراه rollback/backup note باشند. داده مورد پایش مقصد پیش‌فرض write نباشد.
- مدل/قاعده باید version و evidence داشته باشد. threshold و formula در UI توضیح داده شوند؛ فرض‌ها پنهان نمانند.
- AI فقط برای کمک به توضیح متن استفاده شود؛ اجرای SQL را بر مبنای خروجی آزاد مدل انجام نده.
- تست‌های اجراشده، نتیجه، تست‌های اجرا‌نشده و ریسک‌های باقیمانده در تحویل بنویس. ادعای موفقیت بدون اجرای test نکن.
- Commit/push فقط در صورت درخواست/اختیار پروژه انجام شود؛ هر تغییر schema، permission یا production به تأیید کارفرما نیاز دارد.

## ۶. قالب تحویل هر مرحله

هر PR/تغییر تحویلی باید این موارد را داشته باشد:

1. **هدف:** کدام فاز و کدام نیازمندی را پوشش می‌دهد.
2. **تغییرات:** فایل‌ها و رفتارهای تغییرکرده.
3. **تصمیم‌ها:** ADR/فرض تازه و دلیل آن.
4. **داده و امنیت:** queryها، permission، secret handling و اثر بر load.
5. **تست:** دستورهای اجراشده و نتیجه واقعی.
6. **پذیرش:** معیارهای پاس‌شده/باقی‌مانده.
7. **محدودیت‌ها:** نسخه‌های SQL Server، sourceهای پشتیبانی‌نشده، کیفیت داده و known issues.
8. **گام بعدی:** فقط پیشنهاد مرحله بعد، نه اجرای خودکار آن.

## ۷. Definition of Done کلی

قابلیت زمانی Done است که پیاده‌سازی با یکی از اسناد نیازمندی map شده باشد؛ queryها و permissions مشخص باشند؛ migration و retention روشن باشد؛ تست مثبت و منفی داشته باشد؛ کیفیت/تازگی داده در خروجی دیده شود؛ امنیت و عدم افشای secret بررسی شود؛ کاربر بتواند دلیل Insight را بفهمد؛ و README/INSTALL/API docs به‌روز باشند. برای قابلیت تغییردهنده، preview، approval، audit و rollback الزامی است.

## ۸. وابستگی‌های مهم و تصمیم‌های باز

پیش از شروع فازهای ۲ تا ۸، مالک محصول باید نسخه SQL Server و editionها، تعداد instanceها، محل اجرا، repository مناسب، authentication، retention، Query Store policy و منبع فضای آزاد volume را مشخص کند. تا زمان پاسخ، AI باید interface/optionها را طراحی و تصمیم باز ثبت کند، نه اینکه فرض را داخل production behavior hard-code کند.

هر نیاز به بررسی یا تغییر SQL production، فعال‌کردن Query Store، grant مجوز جدید، تغییر فایل‌های دیتابیس، ساخت/حذف index، یا اجرای Job، مجوز اقدام جداگانه می‌خواهد. فقط خواندن اسناد یا ساخت fixture نیازمند این مجوز نیست.
