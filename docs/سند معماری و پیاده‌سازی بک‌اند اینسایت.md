# سند معماری و پیاده‌سازی بک‌اند اینسایت

**موضوع:** طراحی فنی backend برای Insight، پیش‌بینی و پیشنهادهای پیشگیرانه SQL Server
**تهیه‌کننده:** Manus AI
**تاریخ:** ۱۶ نوامبر ۲۰۲۶
**مبنای نیازمندی:** «سند اینسایت و پیش‌بینی DBA» و «سند نیازمندی از سمت مانوس»

## ۱. هدف و محدوده

این سند معماری عملیاتی backend را تعریف می‌کند تا پروژه از polling مستقیم در callbackهای Dash به جمع‌آوری قابل‌ردیابی، نگه‌داری تاریخچه، تحلیل روند و تولید Insightهای قابل‌توضیح برسد. هدف، ساخت مدل ML پیچیده در قدم اول نیست؛ هدف ساخت جریان داده‌ای است که بتوان به اعداد آن اعتماد کرد، کیفیت و ضعف داده را نشان دهد و اقدام حساس را بدون تأیید DBA اجرا نکند.

نسخه اول باید read-only باشد. `CREATE INDEX`, `DROP INDEX`, `ALTER INDEX`, force-plan، اجرای/توقف Job و تغییر configuration در scope اجرای خودکار نیستند. در صورت نیاز بعدی، این موارد به سرویس Action جدا، با مجوز مستقل و تأیید DBA منتقل می‌شوند.

## ۲. معماری هدف

### ۲.۱ اجزا

1. **Web/API application:** داشبورد Dash موجود و API JSON برای خواندن داده‌ها و Insightها. Callbackها UI را render می‌کنند و queryهای سنگین مستقیم اجرا نمی‌کنند.
2. **Collector service:** worker مستقل یا process زمان‌بندی‌شده که از هر SQL Server داده‌های مشخص‌شده را با timeout، retry محدود و ثبت poll health می‌گیرد.
3. **Source adapters:** آداپتورهای جدا برای SQL Agent، Query Store، object/index metadata، database/file capacity، و در آینده waits/availability. هر آداپتور version، permission prerequisite و query cost را مستند می‌کند.
4. **Normalizer/validator:** یکسان‌سازی timestampها، شناسه instance/object، وضعیت‌ها، واحد metricها، و validation داده. داده ناقص حذف پنهانی نمی‌شود؛ collection quality را پایین می‌آورد.
5. **Repository:** ذخیره تاریخچه مشاهده‌شده، خلاصه‌های زمانی، Insightها، وضعیت رسیدگی، metadata، تنظیمات collector و audit.
6. **Analytics engine:** محاسبه rolling baseline، trend، threshold، regression و forecast. منطق تحلیل باید از وب‌فریم‌ورک جدا، deterministic و unit-testable باشد.
7. **Notification dispatcher:** در فاز بعدی، alertهای تأییدشده را به email/webhook تحویل می‌دهد. failure ارسال و retry ثبت می‌شوند.
8. **Action service (آینده):** در MVP وجود ندارد. بعداً برای اجرای اقدام تغییردهنده با credentials و RBAC جداگانه طراحی می‌شود.

### ۲.۲ جریان داده

`Scheduler → Collector → Source adapter → Normalize/validate → Repository → Analytics run → Insight records → API → Dashboard/notification`.

Collector فقط داده می‌خواند. Analytics روی snapshotهای ذخیره‌شده کار می‌کند، نه با query سنگین روی SQL Server در زمان بازشدن صفحه. خطای یک instance یا یک collector نباید داده سایر instanceها را از بین ببرد. API آخرین poll status و freshness را کنار آخرین مقدار metric ارائه می‌کند.

### ۲.۳ شکل استقرار مرحله‌ای

- **مرحله local/single user:** backend و worker می‌توانند در همان برنامه اجرا شوند، ولی به‌صورت ماژول و lifecycle مستقل؛ polling مرورگر تنها محرک جمع‌آوری نباشد.
- **مرحله چندسروره/چندکاربره:** web و worker به processهای جدا تبدیل شوند؛ scheduler مرکزی یا queue اضافه شود و repository اشتراکی داشته باشند.
- **مخزن داده:** adapter مستقل تعریف شود. برای نمونه محلی می‌توان SQLite را فقط برای توسعه یا single-user استفاده کرد؛ برای استقرار چند worker/کاربر، repository ماندگار و پشتیبان‌گیری‌شونده لازم است. گزینه پیشنهادی پایه، SQL Server جداگانه یا PostgreSQL برای repository است. در هیچ‌یک از حالت‌ها، داده تحلیلی به‌طور پیش‌فرض در دیتابیس عملیاتی تحت پایش نوشته نشود.

## ۳. ساختار پیشنهادی کد

بدون بازنویسی یک‌باره، مسئولیت‌ها از فایل‌های فعلی جدا شوند:

```text
app.py                     # composition و route/callbackهای UI
src/api/                   # endpointهای JSON و validation ورودی
src/collectors/            # scheduler، poll orchestration و health
src/sources/sqlserver/     # اتصال، queryها و adapterهای SQL Server
src/domain/                # entityها و status/metric contracts
src/repositories/          # interface و پیاده‌سازی repository
src/analytics/             # rules، baseline، forecast و confidence
src/insights/              # lifecycle، deduplication و severity
src/notifications/         # email/webhook در فاز بعد
src/security/              # auth، RBAC، secret references، audit
migrations/                # migration نسخه‌دار schema
 tests/                    # unit، integration، contract و safety tests
```

این ساختار پیشنهاد است، نه الزام به rename یک‌باره. ابتدا interfaceها و تست‌ها ساخته شوند؛ بعد هر query و منطق محاسبه یک به یک منتقل شود. فایل `db.py` فعلی می‌تواند برای adapter اولیه استفاده شود و در طول مهاجرت شکسته شود.

## ۴. موجودیت‌ها و schema داده

نام فیزیکی جدول‌ها با موتور repository نهایی تطبیق داده شود. حداقل موجودیت‌های منطقی:

### `monitored_instance`

`instance_id`, display name, server reference, SQL version/edition, enabled, timezone, group/tags, created/updated. رمز عبور در جدول plain text ذخیره نشود؛ فقط secret reference به Credential Manager/secret store نگه‌داری شود.

### `collection_run`

`run_id`, instance_id, collector_name, started_at_utc, finished_at_utc, status, error_code, sanitized_error, rows_read, duration_ms, source_version. این جدول منبع canonical برای health/freshness و تشخیص gap است.

### `metric_sample`

`sample_id`, instance_id, scope_type, scope_key, metric_name, observed_at_utc, numeric_value, unit, dimensions_json, quality, source. داده‌های حجیم بر اساس نوع metric partition/retention شوند. مقدارها بدون unit یا context ذخیره نشوند.

### `job_run` و `job_step_run`

شناسه instance/job/run، start/end، status خام SQL Agent و status نرمال‌شده، duration، retry، message redacted، step id/name و source history row. مدل باید اجرای هم‌نام Job در دو instance را از هم جدا کند.

### `query_observation` و `query_plan_observation`

شناسه Query Store به همراه database/instance، plan reference، زمان بازه، تعداد اجرا، میانگین/مجموع/percentileهای موجود برای duration/CPU/logical reads/writes/waits، plan hash و query text reference. متن query و plan XML در صورت ذخیره باید policy دسترسی و retention محدود داشته باشد؛ می‌توان در ابتدا فقط hash و metadata نگه داشت.

### `object_size_snapshot`

instance/database/object/index/partition، observed time، row_count تقریبی، reserved/used/data/LOB pages، اندازه bytes مشتق‌شده و collection quality. raw page counts نگه‌داری شوند تا تبدیل واحد بعداً قابل بازتولید باشد.

### `file_capacity_snapshot`

database/file id/type/path reference، allocated bytes، used/free bytes درون فایل در صورت دسترسی، growth/max size، volume total/free bytes در صورت دسترسی، observed time و quality. فیلدهای filesystem و داخل فایل دیتابیس جدا ذخیره شوند.

### `index_metadata_snapshot` و `index_usage_snapshot`

تعریف index شامل key ordinal/direction، included columns، filter، uniqueness، constraint ownership، type، partition، size. usage شامل seeks/scans/lookups/updates و timestamp شروع SQL Server. هر snapshot immutable و زمان‌دار باشد؛ مقدار cumulative به delta فقط وقتی قابل‌اعتماد تبدیل شود که restart/reset بین دو snapshot شناسایی نشده باشد.

### `insight` و `insight_evidence`

`insight_id`, instance/scope, type, rule_id/version, severity, confidence, status, first_seen, last_seen, expires_at, title, summary, recommendation, dedup_key, created_at. Evidence در جدول جدا با `evidence_type`, source reference, observed period, values, baseline, unit, explanation و quality ذخیره شود. JSON برای payload انعطاف‌پذیر است، ولی فیلدهای لازم برای فیلتر و index جستجو به ستون‌های مشخص تبدیل شوند.

### `insight_event` و `audit_event`

تغییر وضعیت، acknowledge، assign، snooze، feedback و اقدامات انجام‌شده با actor، زمان و قبل/بعد ثبت شوند. رکوردهای audit حذف یا بازنویسی نشوند.

### `baseline_snapshot` و `forecast_snapshot`

موجودیت، metric، روش، پنجره داده، پارامترها/model version، مقدار baseline/forecast، horizon، confidence interval، generated_at و data_quality. این جداسازی امکان مقایسه نسخه الگوریتم و بازسازی خروجی را فراهم می‌کند.

### `collection_policy` و `insight_rule_config`

فواصل جمع‌آوری، فعال‌بودن adapter، پنجره maintenance، آستانه‌ها و notification rule. هر تغییر تنظیمات با نسخه و actor ثبت شود. Secret واقعی در این جدول قرار نگیرد.

## ۵. جمع‌آوری داده و cadence

فواصل زیر نقطه شروع پیشنهادی‌اند؛ DBA باید بتواند per instance تنظیم کند و load test/monitoring آن‌ها را تأیید کند:

| حوزه | cadence آغازین | یادداشت |
|---|---|---|
| وضعیت Jobهای در حال اجرا و poll health | ۳۰ تا ۶۰ ثانیه | query سبک، timeout کوتاه و backoff هنگام خطا |
| تاریخچه Job و schedule | ۱ تا ۵ دقیقه | incremental با watermark و اصلاح late-arriving records |
| Query Store runtime stats | ۵ تا ۱۵ دقیقه | فقط وقتی Query Store فعال و دسترسی مجاز است؛ بازه aggregation را حفظ کند |
| اندازه فایل و فضای داخلی | ۱۵ تا ۶۰ دقیقه | فضای volume از منبع جدا و قابل‌دسترسی خوانده شود |
| row/index size snapshot | روزانه، یا ۶ ساعت در محیط پررشد | جمع‌آوری همه objectها می‌تواند هزینه داشته باشد؛ سقف و sampling تعریف شود |
| index usage/operational counters | ۱۵ تا ۶۰ دقیقه | restart/reset را بشناسد؛ delta نامعتبر را علامت‌گذاری کند |
| physical index statistics | هفتگی/درخواست DBA، خارج از اوج | فقط با محدودیت scope/mode و بررسی اثر بر load/replica |
| config/index metadata snapshot | روزانه و پس از رویداد تغییر | commandهای Job/query text حساس محسوب شوند |

الگوریتم watermark باید overlap امن داشته باشد تا runهایی که با تأخیر در تاریخچه ظاهر می‌شوند از دست نروند. نوشتن repository باید idempotent باشد: اجرای دوباره همان poll رکورد تکراری نیاورد. هر query دارای timeout، limit، cancellation و ثبت مدت باشد. خطاهای permission، timeout، unsupported version و source disabled از هم متمایز شوند.

## ۶. الگوریتم‌های اولیه Insight و Forecast

### ۶.۱ مرحله اول: قواعد و آمار توضیح‌پذیر

برای MVP از threshold و آمار مقاوم استفاده شود، نه ML black-box. هر rule ورودی، window، min sample count، threshold، severity و recovery/hysteresis مشخص دارد. Hysteresis از باز و بسته‌شدن مکرر alert نزدیک آستانه جلوگیری می‌کند.

- **Job runtime baseline:** میانه و percentile مدت اجرا به تفکیک job، روز هفته و slot زمانی. اگر نمونه کافی نیست، fallback به بازه ساده اخیر و confidence پایین.
- **Query regression:** مقایسه runtime/CPU/reads در پنجره‌های مشابه و تشخیص plan hash change؛ صرف plan change به‌تنهایی alert نیست و باید تغییر معنی‌دار در resource/performance هم دیده شود.
- **Capacity forecast:** محاسبه شیب از snapshotهای مرتب‌شده با مقاومت به outlier، تخمین time-to-threshold و بازه عدم‌قطعیت. اگر روند منفی/نوسانی/کم‌نمونه است، نتیجه را «قابل پیش‌بینی نیست» اعلام کند.
- **Object growth:** شیب اندازه و row count بر مبنای snapshots؛ اختلاف ناشی از rebuild/compression/partition switch به‌عنوان structural change علامت‌گذاری شود.
- **Index review candidate:** ترکیب مدت usage window، read/write counters، restart time، Query Store coverage، size، uniqueness/constraint flags، duplicate/overlap و workload metadata. خروجی اولویت بررسی است، نه دستور حذف.

### ۶.۲ کفایت داده و confidence

حداقل تاریخچه قابل تنظیم باشد؛ پیشنهاد شروع: برای baseline زمان‌محور ۱۴ تا ۳۰ روز و برای کاندیدهای حذف index حداقل یک چرخه کسب‌وکار کامل و ترجیحاً ۳۰ روز یا بیشتر. این مقدار universal نیست و باید با workload و SLA تنظیم شود.

Confidence از حداقل این فاکتورها ساخته شود: تعداد نمونه، پوشش بازه، تازگی آخرین داده، پیوستگی collection، restart/reset، تغییر schedule/schema/plan، نوسان metric و کیفیت منبع. ابتدا قواعد ساده و explainable برای confidence ثبت شوند. confidence یک امتیاز کالیبره‌شده تلقی نشود مگر بعداً با نتایج واقعی اعتبارسنجی شده باشد.

### ۶.۳ بازتولیدپذیری

هر خروجی باید rule/model version، input window، parameterها، timestamp، نسخه source query و خلاصه evidence را ذخیره کند. اجرای مجدد analytics روی همان داده و همان نسخه باید نتیجه هم‌ارز دهد. تغییر الگوریتم به معنی نسخه جدید است و نتایج قبلی rewrite نمی‌شوند.

## ۷. تحلیل و ایمنی Index

### ۷.۱ Index catalog

برای هر index، UI/API باید key columns با ordinal و جهت، INCLUDE، filter، unique/constraint بودن، نوع index، اندازه، partition، reads و writes و آخرین فعالیت قابل مشاهده را نشان دهد. Missing-index recommendations از SQL Server یک evidence source است، نه حکم. خود مستند Microsoft محدودیت‌هایی نظیر عدم تضمین ترتیب کلید، پیشنهادهای مشابه، نبود تحلیل هزینه کامل index و پاک‌شدن داده در برخی تغییرات را گوشزد می‌کند [1].

### ۷.۲ استفاده و restart

`sys.dm_db_index_usage_stats` counters را با startup/reset از دست می‌دهد؛ `sqlserver_start_time` در کنار snapshotها ثبت شود و delta فقط برای دو observation با startup یکسان معتبر باشد [2]. اگر restart رخ داده، UI دوره observation را از نو شروع کند و confidence کاندید حذف را پایین بیاورد. در صورت نبود Query Store coverage، وضعیت باید «شواهد workload ناقص» باشد.

### ۷.۳ حذف و ایجاد

- هیچ پیشنهاد خودکار مستقیماً اجرا نمی‌شود.
- indexهای PK/UNIQUE و مواردی که constraint/FK را پشتیبانی می‌کنند از حذف عادی خارج می‌شوند؛ `DROP INDEX` برای indexهای حاصل از PK/UNIQUE کافی نیست و constraint باید از مسیر خودش مدیریت شود [3].
- DDL پیشنهادشده با schema-qualified names، escaped identifiers، پیش‌شرط، version compatibility و rollback script تولید شود.
- اجرا در MVP وجود ندارد. فاز بعدی نیازمند Action API مجزا، role مجاز، تأیید دوباره با نام instance/database/table/index، پنجره نگه‌داری، lock/online/edition بررسی‌شده، timeout و ثبت نتیجه است.
- قبل/بعد از اقدام، Query Store و write overhead مقایسه شوند. اگر outcome بدتر شد، هشدار rollback و اسکریپت بازسازی ارائه شود؛ rollback خودکار تنها پس از طراحی مستقل و تست قابل طرح است.

## ۸. API پیشنهادی

API فقط نمونه منطقی مسیرهاست؛ framework نهایی پس از بررسی dependencyها و سبک پروژه انتخاب شود:

- `GET /api/v1/instances` — فهرست instance و سلامت آخرین collection.
- `GET /api/v1/instances/{id}/insights` — فیلتر status/severity/type/confidence/time.
- `GET /api/v1/insights/{id}` — شرح کامل، evidence، rule version و recommendation.
- `POST /api/v1/insights/{id}/acknowledge` — ثبت بررسی و actor.
- `POST /api/v1/insights/{id}/feedback` — helpful/not useful با توضیح.
- `GET /api/v1/instances/{id}/capacity` — file/object growth snapshots و forecast.
- `GET /api/v1/instances/{id}/indexes` — metadata و usage summary.
- `GET /api/v1/instances/{id}/index-candidates` — فهرست بررسی با evidence و safeguards.
- `GET /api/v1/health` — سلامت application/repository/worker بدون افشای secret.

APIها باید pagination، sort whitelist، server-side filters، response schema version، validation، timeout، correlation id و authorization داشته باشند. query parametrization استفاده شود و نام schema/table/column از user input مستقیم به SQL نچسبد.

## ۹. امنیت، حریم داده و مجوز

1. Credential پایش read-only و حداقل‌مجوز باشد. دسترسی لازم برای هر adapter و SQL Server version در matrix نگه‌داری شود.
2. Secret در repository یا log plain text نشود؛ از secret store/Windows Credential Manager استفاده شود.
3. متن query، execution plan، command و error message ممکن است داده حساس/PII داشته باشند؛ کنترل دسترسی، redaction، retention و export policy لازم است.
4. Web deployment غیرمحلی به authentication/RBAC، HTTPS، CSRF protection و audit نیاز دارد.
5. Collector read identity از action identity جداست. اگر action service آینده اضافه شد، credential آن به‌صورت پیش‌فرض در دسترس read-only worker نباشد.
6. SQLهای جمع‌آوری نسخه‌سنجی و review شوند؛ هیچ SQL پیشنهادی از مدل متنی مستقیماً اجرا نشود.

## ۱۰. مشاهده‌پذیری خود سامانه

برای خود برنامه metrics و logs لازم است: queue depth، poll success rate، collector duration، SQL timeout، repository write latency، analytics duration، تعداد Insight فعال/تکراری، notification delivery و storage/retention. Logها structured باشند و secret/query text حساس را ثبت نکنند. health dashboard حداقل وضعیت هر instance و data freshness را نشان دهد.

## ۱۱. تست و کیفیت

### Unit tests

- تبدیل status و duration SQL Agent، timezone، نیمه‌شب و run طولانی.
- محاسبه rolling median/percentile، رشد، forecast و عدم‌قطعیت روی داده synthetic شامل outlier و gap.
- deduplication، lifecycle، expiry و hysteresis Insightها.
- تشخیص restart و جلوگیری از محاسبه delta index usage روی دو startup متفاوت.
- شناسایی constraint-owned/unique/PK و رد کردن action candidate نامجاز.

### Integration/contract tests

- adapterها روی SQL Server آزمایشی یا fixture نسخه‌بندی‌شده اجرا شوند.
- migration و repository روی نسخه supported آزموده شوند.
- Query Store خاموش، permission ناکافی و SQL version ناسازگار بدون crash و با پیام دقیق مدیریت شوند.
- API فیلتر، pagination، RBAC، redaction و response schema را پوشش دهد.

### Performance/safety tests

- اندازه‌گیری query cost و زمان collection با تعداد زیاد object/index.
- سقف timeout، concurrency limit و cancellation اثبات شود.
- replay همان poll باعث duplicate نشود.
- tests تأیید کنند که مسیر read-only هیچ DDL/DML روی monitored databases اجرا نمی‌کند.
- forecastها روی fixture ثابت قابل بازتولید باشند و عدم کفایت داده را درست گزارش کنند.

## ۱۲. تصمیم‌های معماری لازم پیش از توسعه

1. نسخه‌ها و editionهای SQL Server مورد پشتیبانی.
2. Query Store در دیتابیس‌های هدف فعال است یا فقط باید وضعیت آن گزارش شود.
3. نصب اولیه local/single-user است یا از ابتدا multi-instance/multi-user.
4. Repository جداگانه چه موتوری دارد و کجا backup می‌شود.
5. منبع فضای آزاد volume در Windows/Linux/VM/cloud چیست و آیا دسترسی آن مجاز است.
6. retention داده‌های Query Store-derived، object size، plan و Insight چقدر است.
7. حداقل مجوز قابل‌قبول برای performance DMVs و physical stats.
8. نسخه اول کاملاً read-only می‌ماند؛ هر نیاز به اجرای DDL باید به ADR و بررسی امنیت جدا ارجاع شود.

تا روشن‌شدن این تصمیم‌ها، توسعه باید interface و adapter قابل‌تعویض بسازد و فرض‌های deployment را در کد hard-code نکند.

## ۱۳. ترتیب اجرای فنی

1. استخراج قرارداد status/job فعلی و افزودن تست؛ اصلاح Gantt و صحت freshness.
2. ایجاد migrations و repository interface؛ ذخیره poll health و تاریخچه Job.
3. انتقال polling از UI callback به collector قابل اجرا؛ اول یک instance و read-only.
4. افزودن capacity/object snapshots و Query Store adapter اختیاری.
5. پیاده‌سازی rule engine و baselineهای ساده، Insight/evidence lifecycle و API خواندنی.
6. افزودن dashboard مرکز Insight، جزئیات evidence و feedback DBA.
7. افزودن index inventory و candidate review فقط‌خواندنی، سپس کالیبراسیون و تست روی workload آزمایشی.
8. پس از RBAC و audit، جداگانه ارزیابی notification و action service.

هر مرحله باید migration، تست، مستندات اجرا و acceptance criteria خودش را داشته باشد. توسعه نباید همه queryها و قابلیت‌ها را در یک commit بزرگ به `app.py` اضافه کند.
