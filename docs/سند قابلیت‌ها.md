# سند قابلیت‌ها

**موضوع:** قابلیت‌های پیشنهادی برای توسعه SqlServerAgentStatus
**تهیه‌کننده:** Manus AI
**تاریخ:** ۱۶ نوامبر ۲۰۲۶
**ارتباط با سند دیگر:** این سند مکمل «سند نیازمندی از سمت مانوس» است. سند قبلی وضعیت موجود و نیازهای پایه را بررسی می‌کند؛ این سند ایده‌های توسعه محصول را شرح می‌دهد.

## هدف و شیوه اولویت‌بندی

قابلیت‌های زیر برای تبدیل ابزار فعلی مشاهده SQL Server Agent به محصولی کامل‌تر پیشنهاد شده‌اند. این پیشنهادها از مسیر موجود پروژه—دریافت Jobها، وضعیت اجرا، تاریخچه و داشبورد—شروع می‌کنند و قابلیت‌های توسعه‌ای را از اصلاحات پایه جدا نگه می‌دارند.

اولویت «زیاد» یعنی قابلیت برای ارزش عملیاتی روزمره یا اعتماد به محصول لازم است. «متوسط» یعنی پس از پایدارشدن هسته، ارزش قابل‌توجه دارد. «توسعه‌ای» یعنی مناسب نسخه‌های بعدی یا محیط‌های بزرگ‌تر است. اندازه‌ها برآورد نسبی‌اند: کم، متوسط و زیاد. این‌ها برآورد طراحی هستند و با انتخاب معماری و تعداد سرورها می‌توانند تغییر کنند.

## ۱. قابلیت‌های نزدیک به محصول فعلی

### ۱.۱ نمای تقویم زمان‌بندی Jobها

**کاربرد:** مدیر بتواند ببیند هر Job چه زمانی برنامه‌ریزی شده، چه زمان‌هایی هم‌پوشانی دارند و در چه بازه‌ای احتمال بار زیاد وجود دارد.

**رفتار پیشنهادی:** نماهای روزانه، هفتگی و ماهانه داشته باشد. زمان اجرای برنامه‌ریزی‌شده از scheduleهای SQL Server Agent نمایش داده شود و اجرای واقعی به‌عنوان لایه‌ای جدا روی همان خط زمانی دیده شود. Jobهای بدون schedule از Jobهای زمان‌بندی‌شده متمایز باشند.

**مسیر پیاده‌سازی:** خواندن scheduleها از `msdb`، نرمال‌سازی recurrenceهای یک‌باره/روزانه/هفتگی/ماهیانه به زمان‌های قابل نمایش، و افزودن نمای calendar کنار فهرست و Gantt موجود. محاسبه زمان بعدی باید از قواعد Agent پیروی کند؛ صرفاً ترکیب `active_start_date` و `active_start_time` برای recurrenceهای پیچیده کافی نیست.

**اولویت/اندازه:** زیاد / متوسط.

### ۱.۲ هشدار و اعلان قابل تنظیم

**کاربرد:** تیم از شکست یا تأخیر Job باخبر شود، حتی وقتی داشبورد باز نیست.

**قواعد اولیه:** شکست Job، شکست چندباره، اجرا نشدن تا موعد مورد انتظار، طولانی‌شدن اجرا نسبت به مدت معمول، و متوقف‌بودن یا غیرفعال‌شدن ناخواسته Jobهای منتخب.

**رفتار پیشنهادی:** هر قاعده دامنه، شدت، آستانه، بازه سکوت، مقصد اعلان و سیاست تکرار داشته باشد. رخدادهای `critical/high/warning/info` deduplicate شوند، قابل تأیید/acknowledge باشند و زمان شروع، آخرین وضعیت، پیام پاک‌سازی‌شده و پیوند به جزئیات را حمل کنند. Email و Webhook هر دو کانال هدف نسخه عملیاتی‌اند؛ ارسال واقعی تنها پس از تنظیم destination و test delivery فعال شود.

**مسیر پیاده‌سازی:** موتور rule در backend/worker، جدول نگه‌داری رخدادها، مقصدهای Email/Webhook، صف پایدار outbox و ثبت تلاش‌های ارسال. Webhook با HTTPS و HMAC امضا شود؛ retry محدود/backoff و dedup/cooldown داشته باشد. ارسال اعلان از callback صفحه انجام نشود تا بستن مرورگر موجب از دست‌رفتن هشدار نشود.

**اولویت/اندازه:** زیاد / متوسط تا زیاد.

### ۱.۳ مرکز رخدادها و مدیریت رسیدگی

**کاربرد:** فهرست خطاها فقط نمایش لحظه‌ای نباشد؛ تیم بداند کدام رخداد باز است، چه کسی آن را دیده و چه زمانی رفع شده است.

**رفتار پیشنهادی:** رخدادها بر اساس سرور، Job، قاعده، شدت و وضعیت فیلتر شوند. وضعیت‌هایی مانند جدید، تأییدشده، در حال بررسی، رفع‌شده و تکرارشده داشته باشند. رخداد مشابه با کلید مشترک در یک issue گروه‌بندی شود و تاریخچه تغییر وضعیت نگه‌داری شود.

**مسیر پیاده‌سازی:** ذخیره alertها به‌شکل entity مستقل از `sysjobhistory`، با شناسه run مرتبط و audit trail. از پاک‌کردن سابقه برای پنهان‌کردن اعلان استفاده نشود؛ acknowledge تنها وضعیت رسیدگی را عوض کند.

**اولویت/اندازه:** زیاد برای تیم چندنفره / متوسط.

### ۱.۴ تاریخچه گسترده و روند مدت اجرا

**کاربرد:** پاسخ به پرسش‌هایی مانند «این Job چه زمانی کند شد؟»، «نرخ موفقیت هفته چقدر بود؟» و «مدت اجرا رو به افزایش است یا نه؟».

**رفتار پیشنهادی:** بازه انتخابی روز/هفته/ماه/بازه سفارشی، تعداد اجرا، نرخ موفقیت، مدت میانه و صدک‌های مدت، بیشترین مدت و نمایش روند. مقایسه دو بازه زمانی و دانلود CSV نیز فراهم شود.

**مسیر پیاده‌سازی:** ابتدا از داده تاریخی موجود در `msdb` استفاده شود، ولی برای retention پایدار و گزارش‌های چندماهه یک repository اختصاصی با سیاست نگه‌داری اضافه شود. داده خام، خلاصه روزانه و جزئیات Stepها retention جدا داشته باشند.

**اولویت/اندازه:** زیاد / متوسط تا زیاد.

### ۱.۵ دسته‌بندی، برچسب و مالک Job

**کاربرد:** نام Job همیشه برای تعیین واحد کسب‌وکار، محیط و اهمیت کافی نیست؛ دسته‌بندی مبتنی بر نقطه و زیرخط قابل اتکا نیست.

**رفتار پیشنهادی:** برای هر Job برچسب‌هایی مانند سامانه، تیم مالک، محیط، سطح اهمیت و پنجره مجاز اجرا تعیین شود. فیلتر و گزارش بر اساس این برچسب‌ها کار کند. برچسب‌ها باید از metadata محلی یا پایگاه تنظیمات محصول بیایند و نام اصلی Job را تغییر ندهند.

**مسیر پیاده‌سازی:** جدول metadata جدا بر اساس `instance_id + job_id`؛ برای ورود اولیه قابلیت mapping بر اساس الگوی نام و فایل CSV فراهم شود. تغییرات metadata در audit log ثبت شوند.

**اولویت/اندازه:** زیاد / کم تا متوسط.

### ۱.۶ صفحه وضعیت و سلامت منبع داده

**کاربرد:** مدیر تشخیص دهد داده واقعاً تازه است یا داشبورد صرفاً آخرین پاسخ موفق را نشان می‌دهد.

**رفتار پیشنهادی:** زمان آخرین poll موفق، آخرین خطا، مدت query، زمان پاسخ SQL Server، تعداد Job خوانده‌شده و سن داده برای هر instance نمایش داده شود. وضعیت اتصال از وضعیت سلامت SQL Agent جدا باشد.

**مسیر پیاده‌سازی:** ثبت poll result مستقل از داده Job، شامل `started_at`, `completed_at`, `duration_ms`, `status`, `error_code`. health endpoint و نشانگر stale بر اساس آستانه تنظیم‌شده اضافه شود.

**اولویت/اندازه:** زیاد / کم تا متوسط.

## ۲. قابلیت‌های مناسب برای تیم‌ها و چند سرور

### ۲.۱ چند Instance و گروه‌بندی Fleet

**کاربرد:** چند SQL Server از یک داشبورد دیده شوند و مدیر بتواند هم نمای کل محیط و هم نمای یک سرور را بررسی کند.

**رفتار پیشنهادی:** هر instance نام نمایشی، محیط، گروه، وضعیت دسترسی و تنظیم اتصال مستقل داشته باشد. فهرست Fleet تعداد Jobهای در حال اجرا، شکست‌ها و وضعیت poll را خلاصه کند. خطای یک instance نباید سایر سرورها را از نمایش خارج کند.

**مسیر پیاده‌سازی:** تعریف `Instance` با secret reference مستقل، افزودن `instance_id` به کلید همه داده‌ها، و جداسازی جمع‌آوری هر سرور در workerها. پیکربندی اعتبارنامه‌ها و سطح دسترسی باید per-instance باشد.

**اولویت/اندازه:** زیاد در محیط چندسروره / زیاد.

### ۲.۲ داشبوردهای شخصی‌سازی‌شده و فیلترهای ذخیره‌شده

**کاربرد:** DBA، اپراتور و مدیر سامانه نیازمند نمای متفاوتی از همان اطلاعات هستند.

**رفتار پیشنهادی:** کاربر بتواند فیلترهای ثابت مانند «Jobهای بحرانی»، «خطاهای امروز» یا «Jobهای تیم پرداخت» را ذخیره کند و کارت‌های داشبورد را بر اساس انتخاب خود مرتب کند. تنظیمات هر کاربر از تنظیمات مشترک سامانه جدا باشد.

**مسیر پیاده‌سازی:** ابتدا filter presetهای مدیریتی و قابل اشتراک، سپس layout شخصی‌شده. ذخیره تنظیمات UI در server-side user preferences انجام شود، نه فقط در حافظه مرورگر.

**اولویت/اندازه:** متوسط / متوسط.

### ۲.۳ گزارش زمان‌بندی‌شده

**کاربرد:** دریافت‌کنندگان لازم نباشد هر روز برنامه را باز کنند تا خلاصه سلامت را ببینند.

**رفتار پیشنهادی:** گزارش روزانه یا هفتگی از Jobهای شکست‌خورده، Jobهای بدون اجرا، مدت‌های غیرعادی، نرخ موفقیت و رخدادهای تأییدنشده ارسال شود. انتخاب گیرندگان، زمان ارسال و فیلتر دامنه در اختیار مدیر باشد.

**مسیر پیاده‌سازی:** ساخت گزارش از داده repository، renderer ثابت HTML/CSV و scheduler سمت سرور. اجرای گزارش باید timezone، تعطیلات و خطای تحویل را ثبت کند.

**اولویت/اندازه:** متوسط / متوسط.

### ۲.۴ پنجره نگه‌داری و سکوت هوشمند هشدارها

**کاربرد:** ارتقا یا کار برنامه‌ریزی‌شده باعث موج هشدار کاذب نشود، اما رخداد بحرانی خارج از پنجره کنترل‌نشده نماند.

**رفتار پیشنهادی:** پنجره نگه‌داری برای یک instance، گروه یا Job تعریف شود؛ اعلان‌ها یا متوقف شوند یا با شدت پایین‌تر ثبت شوند. بازه سکوت و زمان پایان باید واضح باشد و گزارش تغییرات باقی بماند.

**مسیر پیاده‌سازی:** جدول maintenance window با timezone و recurrence، ارزیابی آن در موتور alert و ثبت رخدادهای suppressشده. امکان لغو و پایان زودهنگام فقط با دسترسی مدیریتی باشد.

**اولویت/اندازه:** متوسط برای محیط عملیاتی / متوسط.

### ۲.۵ نقشه وابستگی Jobها و پنجره‌های کاری

**کاربرد:** تشخیص شود شکست کدام Job زنجیره پایین‌دستی را متأثر می‌کند و زمان پایان زنجیره چه بوده است.

**رفتار پیشنهادی:** نمایش گراف وابستگی بر پایه stepهای اجراکننده Job دیگر، scheduleها و وابستگی‌های ثبت‌شده توسط کاربر. جریان داده با وضعیت هر گره و مدت واقعی آخرین run دیده شود.

**مسیر پیاده‌سازی:** استخراج ارتباط‌های قابل تشخیص از `sysjobsteps` و تعریف dependency دستی برای مواردی که از SQL قابل استنتاج نیستند. قواعد inferred از قواعد قطعی جدا نشان داده شوند تا رابطه احتمالی به‌عنوان حقیقت عرضه نشود.

**اولویت/اندازه:** توسعه‌ای / زیاد.

## ۳. قابلیت‌های پیشرفته‌تر برای نسخه‌های بعد

### ۳.۱ تشخیص ناهنجاری و baseline مدت اجرا

**کاربرد:** به‌جای آستانه ثابت، تغییر غیرمعمول نسبت به الگوی همان Job تشخیص داده شود؛ مثلاً Job معمولاً ۲ دقیقه است اما امروز ۱۵ دقیقه شده است.

**رفتار پیشنهادی:** baseline بر اساس روز هفته، ساعت و بازه اخیر محاسبه شود. در ابتدا فقط هشدار توضیح‌پذیر صادر کند؛ مانند «مدت اجرا ۳٫۲ برابر میانه ۳۰ اجرای مشابه است». آستانه و دوره یادگیری قابل مشاهده باشد.

**مسیر پیاده‌سازی:** شروع با آمار مقاوم مانند median و MAD/percentile به‌جای مدل پیچیده. داده ناقص، تغییر schedule و دوره‌های maintenance از محاسبه baseline کنار گذاشته یا نشانه‌گذاری شوند. مدل خودکار تا داشتن history کافی فعال نشود.

**اولویت/اندازه:** متوسط / متوسط تا زیاد.

### ۳.۲ مقایسه پیکربندی و تغییرات Job

**کاربرد:** مشخص شود command، زمان‌بندی، owner، فعال‌بودن یا تعداد Stepهای Job چه زمانی تغییر کرده است.

**رفتار پیشنهادی:** snapshotهای نسخه‌ای از metadata Job ذخیره شوند. diff تغییرات و کاربری که تغییر را انجام داده نمایش داده شود، در صورت قابل‌دسترسی‌بودن audit مربوط. هشدار تغییر غیرمنتظره برای Jobهای حیاتی قابل تنظیم باشد.

**مسیر پیاده‌سازی:** snapshot منظم از فیلدهای مجاز `sysjobs`, `sysjobsteps`, scheduleها؛ رمز/secretهای درون command باید redact یا محدود شوند. برای انتساب تغییر به کاربر، منبعی مانند SQL Audit یا trace معتبر لازم است؛ صرف اختلاف دو snapshot مشخص نمی‌کند چه کسی تغییر را انجام داده است.

**اولویت/اندازه:** متوسط / متوسط تا زیاد.

### ۳.۳ اقدام عملیاتی از داخل داشبورد

**کاربرد:** کاربر مجاز بتواند Job را اجرا یا متوقف کند، بدون رفتن به SSMS.

**رفتار پیشنهادی:** دکمه اجرای دستی یا توقف فقط با نقش عملیاتی، تأیید صریح، نمایش سرور و Job هدف، و ثبت کامل audit در دسترس باشد. عملیات destructive یا تغییر تعریف Job در نسخه اول ارائه نشود. نتیجه درخواست و run ID برگردانده شود.

**مسیر پیاده‌سازی:** API command جدا از read-only collector، RBAC، CSRF protection، audit log، idempotency و timeout. credential اجرای عملیات از credential خواندن جدا باشد. در طراحی پیش‌فرض بهتر است محصول read-only بماند و قابلیت نوشتن opt-in و محدود باشد.

**اولویت/اندازه:** توسعه‌ای / زیاد، ریسک امنیتی زیاد.

### ۳.۴ پایش سلامت SQL Server فراتر از Agent

**کاربرد:** کاربر از همان محیط برای دیدن CPU، حافظه، I/O، blocking، waits و مشکلات عملکردی استفاده کند.

**رفتار پیشنهادی:** ماژول‌های مستقل برای وضعیت instance، منابع سیستم و شاخص‌های performance ارائه شوند. داشبورد Agent و داشبورد performance از نظر منبع و نرخ جمع‌آوری جدا بمانند؛ هر نمودار واحد، بازه زمانی و روش محاسبه داشته باشد.

**مسیر پیاده‌سازی:** فهرست metric محدود و کم‌هزینه تعریف شود، سپس collector و repository آن به شکل plugin/module اضافه شوند. دسترسی‌های لازم از DBA بررسی شود و اثر queryها بر SQL Server با benchmark اندازه‌گیری شود. query text و اطلاعات حساس پیش‌فرض پنهان یا redact شوند.

**اولویت/اندازه:** توسعه‌ای / زیاد تا بسیار زیاد.

### ۳.۵ API، Webhook و اتصال به سامانه‌های تیمی

**کاربرد:** رخدادها به سیستم ticketing یا observability سازمانی بروند و داده از ابزارهای دیگر قابل مصرف باشد.

**رفتار پیشنهادی:** API نسخه‌دار برای خواندن instances, jobs, runs, alerts و تغییر lifecycle مجاز؛ Email و Webhook امضاشده برای alertها. مقصدهای متداول مانند Teams/Slack، ServiceNow یا ابزارهای مشابه از طریق webhook عمومی پوشش داده شوند؛ اتصال اختصاصی بعداً بر اساس نیاز انتخاب شود.

**مسیر پیاده‌سازی:** ابتدا API read-only با pagination و RBAC، سپس webhook با امضای HMAC، retry محدود، backoff و dead-letter queue. secretهای webhook در vault/credential store نگه‌داری و امکان rotate فراهم شود.

**اولویت/اندازه:** متوسط / متوسط تا زیاد.

### ۳.۶ SLA و تقویم کسب‌وکار

**کاربرد:** موفقیت صرفاً بر اساس وضعیت آخرین اجرا سنجیده نشود؛ Job در زمان موردنیاز کسب‌وکار تکمیل شده باشد.

**رفتار پیشنهادی:** برای Jobهای منتخب موعد، پنجره مجاز، حداقل نرخ موفقیت، حداکثر مدت و تقویم روزهای کاری تعریف شود. گزارش نقض SLA همراه با دلیل قابل پیگیری ارائه شود.

**مسیر پیاده‌سازی:** metadata مربوط به SLA را از schedule فنی جدا نگه دارید؛ timezone، تعطیلات، اجرای مجدد و maintenance window را لحاظ کنید. تعریف SLA را نسخه‌دار و ممیزی‌پذیر نگه دارید.

**اولویت/اندازه:** متوسط در سامانه‌های کسب‌وکارمحور / متوسط تا زیاد.

## ۴. پیشنهاد مسیر انتشار

### نسخه پایه قابل اتکا

ابتدا ایرادهای صحت و وضعیت داده رفع شوند: Gantt، mapping status، اجرای بعدی، نشانگر تازگی اطلاعات، تست‌های خودکار و پیام خطای امن. connection فعلی حفظ شود و foundation مهاجرت به registry چندسروره بدون حذف Credential موجود آماده شود.

### نسخه عملیاتی SQL Agent

سپس registry و نمای Fleet سلامت سرورها، alertهای قابل تنظیم، مرکز رخدادها و Email/Webhook اضافه شوند؛ بعد تاریخچه و روند، دسته‌بندی/مالک Job و گزارش زمان‌بندی‌شده تکمیل شوند. این ترکیب به DBA امکان تشخیص، رسیدگی و اعلان را می‌دهد، بدون افزودن ریسک اجرای command از داشبورد.

### نسخه تیمی و چندسروره

پس از تثبیت registry/health و alerting پایه، collector مرکزی/worker، گروه‌بندی fleet، RBAC، پنجره نگه‌داری و API کامل شوند. این مرحله مرز مهم معماری است؛ polling مرورگر برای چند کاربر و چند سرور جایگزین collector مرکزی نیست.

### نسخه توسعه‌یافته

در صورت نیاز مشتریان، تشخیص ناهنجاری، نقشه وابستگی، مقایسه تغییرات، SLA و پایش عملکرد عمومی SQL Server بررسی شوند. قابلیت اجرای/توقف Job از UI فقط پس از طراحی امنیت، ممیزی و جداسازی credential به‌عنوان گزینه مستقل ارزیابی شود.

## ۵. معیار انتخاب قابلیت بعدی

پیش از شروع هر قابلیت، این پرسش‌ها پاسخ داشته باشند:

1. چه کاربری از آن استفاده می‌کند و مسئله روزمره‌اش چیست؟
2. داده لازم از کدام منبع SQL Server می‌آید و حداقل مجوز لازم چیست؟
3. آیا باید history دائمی ذخیره شود؟ اگر بله، retention و حجم تخمینی چیست؟
4. رفتار در قطع اتصال، داده ناقص، retry و منطقه زمانی چیست؟
5. آیا قابلیت فقط خواندنی است یا عملیاتی را روی SQL Server اجرا می‌کند؟
6. چه آزمون‌هایی نشان می‌دهند قابلیت برای وضعیت‌های موفق، خطا و مرزی درست است؟
7. معیار پذیرش کمی چیست؛ مانند کاهش زمان تشخیص یا پوشش تعداد instance؟

## ۶. جمع‌بندی اولویت پیشنهادی

بهترین قابلیت‌های بعدی برای ارزش زیاد و ریسک قابل‌کنترل عبارت‌اند از: تقویم schedule، هشدار ایمیلی/webhook، مرکز رخدادها، تاریخچه و روند، metadata مالک/اهمیت Job و سلامت منبع داده. چندسروره‌شدن، repository تاریخی و collector مرکزی ارزش معماری بالایی دارند، اما بهتر است پیش از توسعه وسیع گزارش‌ها طراحی شوند. اقدام مستقیم روی Job و گسترش به performance monitoring جذاب‌اند، ولی به‌ترتیب نیازمند کنترل امنیتی جدی و دامنه فنی بزرگ‌تری هستند.
